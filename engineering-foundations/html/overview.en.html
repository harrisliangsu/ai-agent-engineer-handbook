From Prompt to Harness: The Three-Layer Evolution of LLM Application Engineering

English · 中文

Historical v1 merge, frozen. This English text follows the Chinese original and is not updated to match the later four chapters.

Research date: 2026-05-01 · Mode: deep-research ultradeep · Search paths: 18 in parallel (Chinese and English mixed)

Executive Summary

In the nine years from the 2017 Transformer architecture paper [1] to 2026, “how to make an LLM actually run in production” went through three paradigm shifts: prompt engineering (Prompt Engineering, the main line of 2022-2023) → context engineering (Context Engineering, formally named by Karpathy and others from 2024 [5][6]) → harness engineering (Harness Engineering, named by Mitchell Hashimoto in February 2026 [8][31]).

The three are not a relationship of replacement. They are stacked abstractions: prompt engineering cares about “how this one sentence is written,” context engineering cares about “what the model sees at this moment of inference,” and harness engineering cares about “what environment the whole agent runs in, and how, when it errs, it stops making the same mistake again.”

This essay is organized around those three layers:

  • Part I starts from the Transformer attention mechanism and covers the LLM training stack (pretraining → post-training → fine-tuning, including SFT/DPO/GRPO/RLAIF/RLVR/LoRA/QLoRA/distillation), inference and decoding strategies, then the classic prompt techniques such as CoT/ReAct/ToT/Self-Refine and automatic methods such as APE/OPRO.
  • Part II dissects the physical constraints of context engineering (O(N²) attention, Lost-in-the-Middle [2], the RULER benchmark [12]), full-stack RAG selection (four generations of evolution, embedding models and the MTEB leaderboard, vector-store benchmarks, hybrid retrieval + reranking, query rewriting, GraphRAG / Self-RAG / CRAG / Agentic RAG), the four leading memory systems (MemGPT-Letta / mem0 / Zep / Anthropic Memory Tool), and the MCP / A2A protocol ecosystem.
  • Part III takes apart the seven components of harness engineering: tool integration, the sandbox, the LLM gateway, the inference server (vLLM / SGLang), observability (LangSmith / Langfuse / Helicone / Phoenix), evaluation (DeepEval / RAGAS / Promptfoo / Braintrust), and guardrails (NeMo Guardrails), and gives the mainstream options for agent orchestration together with a reference architecture for a “complete production stack.”

The end of the essay gives a technology-selection list and a statement of limitations for three typical scenarios (personal learning / a startup MVP / enterprise production).

Part I: Prompt Engineering (including Transformer / LLM foundations)

1.1 Starting point: the Transformer and attention

In Attention Is All You Need [1] in 2017, Vaswani et al. proposed the Transformer architecture, taking recurrence (RNN) and convolution (CNN) out of sequence modeling and leaving only “attention.” The core idea is extremely plain: every token in the sequence does a weighted aggregation with every other token through three matrices, Query / Key / Value, and the weights are decided by softmax(QK^T / √d). Two direct consequences of this design are global visibility (any position can see any other position directly, with no need to pass information step by step) and full parallelism (it no longer has to run forward one time step at a time, the way an RNN does).

But from the day it was born, the Transformer has carried a mathematical burden: standard self-attention is O(N²) in both time and VRAM for a sequence of length N [a detailed argument on this point can be found in several surveys from 2026 [11][39]]. Expand the context window from 32K to 128K and the compute is not 4×. It is 16×. This one mathematical fact drove billions of dollars of engineering investment across 2022-2026.

A series of variants was born around the question of how to punch through the O(N²) wall: - Linear Attention (Katharopoulos 2020) uses a kernel feature map plus the associativity of matrix multiplication to avoid the explicit attention matrix, and brings the complexity down to O(N); - Sparse Attention (for example Longformer / BigBird) lets each token look only at a local window plus a few global tokens; - Flash Attention (Dao, from 2022) does not change the algorithm. It changes the engineering — it splits the attention computation, by tiling, into small blocks that fit in the GPU’s on-chip SRAM, and avoids writing the N×N matrix back to HBM. Flash Attention 4 was released in March 2026 and reaches 1605 TFLOPs/s and 71% hardware utilization on an NVIDIA B200 GPU [as described in the 2026 survey of attention mechanisms]; - Paged Attention (the vLLM team, 2023) borrows the idea of operating-system virtual memory, cuts the KV cache into pages of 16 tokens, and keeps VRAM fragmentation under 4% [10]; - Local Attention / Sliding Window Attention, used for long-sequence optimization in Mistral, Qwen, and others.

By 2026 these techniques are no longer a choice of one or the other. They are mixed and stacked by layer and by block: the lower layers of the model use Sliding Window to control cost, the critical layers use Full Attention to keep expressive power, and at inference time everything goes through Flash + Paged optimization.

Scaling Laws are another main line that evolved in parallel with the Transformer. Kaplan et al. in 2020 proposed a power-law relationship among parameter count, data volume, and compute. Hoffmann et al. in 2022 (Chinchilla) corrected “how many tokens should train a model of how many parameters” — the conclusion was that the previous mainstream (GPT-3, for example) was severely under-trained. The key turn in 2025-2026 is this: the center of gravity moved from “more data” to “higher-quality data.” Once Common Crawl has already been consumed and synthetic data is on the rise, what the laws attend to is no longer the token count itself, but the information density and diversity of the tokens.

1.2 The LLM training stack: pretraining → post-training → fine-tuning

By 2026 the standard template of the training stack has settled into “three stages” — pretraining (Pretraining) → post-training (Post-training) → task-level fine-tuning (Task-specific Fine-tuning). In State of LLMs 2025 [22], Sebastian Raschka remarks: “The standard recipe 12 months ago was to pretrain on a few trillion tokens and then run RLHF; that recipe is dead. From DeepSeek-R1 to Nemotron 3 Super to GPT-5.3 Codex, every major model released over the past year used a different post-training stack.”

Pretraining

The task is very simple: next-token prediction on a huge corpus, with backpropagation of a cross-entropy loss. The engineering difficulty is extreme:

  • Data: a mix of the public web (Common Crawl, C4, RefinedWeb) + code (GitHub, StackOverflow) + academic sources (arXiv, Wikipedia, books) + multilingual data + synthetic data (distilled from a stronger model)
  • Mix strategy: run the high-quality data for extra epochs (curriculum learning), and raise the proportion of math / code / reasoning data
  • Infrastructure: GPU clusters from a thousand to ten thousand cards, 3D parallelism (data / tensor / pipeline / Sequence parallel), checkpointing, fault-tolerant recovery
  • Hyperparameters: BF16 / FP8 mixed precision, the Lion / AdamW optimizers, a cosine learning rate, warmup
  • Deduplication / detoxification / PII filtering of the data

The product of pretraining is a base model. It can continue a text, but it cannot “hold a conversation.” Give it “How is the weather today?” and it goes on with a rambling forum-style aside rather than answering you. Turning it into an interactive assistant, the way ChatGPT is one, takes post-training.

Post-training

Across 2024-2026, post-training was split into three relatively orthogonal stages [23][24]: SFT (teach the model to speak) → preference alignment (teach the model to say what people like) → reasoning reinforcement (make the model more accurate on verifiable tasks). The order matters.

SFT (Supervised Fine-Tuning)

Continue training the base model on human-written “instruction-answer” pairs (in the style of Alpaca / Dolly / OpenAssistant), so that it learns instruction following and the dialogue format. SFT teaches the model how to speak — producing structured output, following the system prompt, using an appropriate degree of politeness, and so on. Technically it differs little from pretraining. The difference is mostly in the data.

RLHF (Reinforcement Learning from Human Feedback)

The signature technique of OpenAI’s InstructGPT / ChatGPT. The process has three steps: (a) collect human preference pairs (“answer A is better than B”); (b) train a reward model to learn those preferences; (c) fine-tune the original model with the PPO algorithm, using the reward model’s score as the reward. PPO is extremely complex to implement. It has to keep 4 models at once (actor, critic, reference, reward). VRAM explodes, and training is unstable.

DPO (Direct Preference Optimization)

“RLHF without RL,” proposed by Rafailov et al. at Stanford in 2023. The core insight: after a closed-form rewrite of the RLHF objective, it turns out the original model can be trained directly on preference pairs, with no reward model and no PPO. A simple binary-classification loss is enough. The result: training is 10x more stable, the VRAM footprint drops by half, and the quality matches PPO RLHF or is even better. From 2024 on, the great majority of open-source models (Llama 3, Qwen 2/3, the Mistral series) switched to DPO or a variant of it (IPO / KTO / SimPO) in place of PPO.

GRPO (Group Relative Policy Optimization)

Proposed by the DeepSeek team in 2024, and the core algorithm behind the breakout of the R1 series [22][23]. GRPO removes PPO’s critic network (the main source of PPO’s training instability) and switches to a “within-group relative advantage” — for the same prompt, sample N answers; the advantage of each answer = that answer’s reward minus the within-group mean; then update with a PPO-style policy gradient. On verifiable tasks such as math and code the effect is striking, and it brought online RL back into the mainstream.

RLAIF (Reinforcement Learning from AI Feedback)

First systematized in Anthropic’s 2022 paper Constitutional AI: a stronger LLM replaces humans in labeling preference pairs, which sharply cuts the cost of data. In 2025-2026 RLAIF has become the common practice — base-model alignment uses RLAIF, and critical safety settings use human feedback as the last gate.

RLVR (Reinforcement Learning with Verifiable Rewards)

It took off in the second half of 2025 on OpenAI o1 / DeepSeek-R1. The core idea: on tasks such as math problems, code, and unit tests, where “the answer can be verified automatically by a program,” the reward signal does not come from human preference or from a reward model. It comes from a hardcoded verifier (run the unit tests, compare against the reference answer). This avoids the reward model’s cheating problem (reward hacking) and pushed reasoning ability to a new height. GRPO + RLVR is R1’s golden combination.

DAPO (Decoupled Clip and Dynamic Sampling Policy Optimization) and other new algorithms of 2026 continue the engineering optimization on top of GRPO (dynamic sampling, layered clipping).

Task-level fine-tuning (Fine-Tuning)

If what you have is not the resources to “train a new base model,” but the job of “doing domain adaptation on an existing open-source model,” then fine-tuning is your tool. There is a critical cost divide here [25]:

Method VRAM, 7B model Hardware cost Quality retained Suited to
Full Fine-Tune 100-120 GB $50K (H100) 100% (baseline) Latency-sensitive + highest accuracy
LoRA ~25 GB $10K (A100) 95-98% Fast experiments + multiple adapters
QLoRA ~6 GB $1.5K (RTX 4090) 80-90% VRAM at the limit + isolation across many customers
Distillation depends on the student medium depends on the task Inference latency / cost pushed to the extreme
  • LoRA (Low-Rank Adaptation, Hu et al. 2021) adds only a pair of low-rank matrices A·B beside the weight matrix, freezes the original weights, and trains just 0.2-0.3% of the parameters. It fits the case where you have to keep several lightweight adapters for different customers / tasks / settings. Switching adapters means swapping one small file of a few hundred MB.
  • QLoRA (Dettmers 2023) = a 4-bit quantized base model + LoRA. It compresses the base model’s resident VRAM from ~26 GB (fp16, 7B) down to ~4 GB, so a single consumer GPU (a 4090 or a 3090) can fine-tune a 7B model. The quality loss is about 5-10%.
  • PEFT (Parameter-Efficient Fine-Tuning) is an umbrella term covering LoRA, QLoRA, Prefix Tuning, Prompt Tuning, Adapter Tuning, IA³, and others. HuggingFace’s peft library is the de facto standard.
  • Distillation (Knowledge Distillation) takes another path: a large model (the teacher) generates a large amount of data, and a small model (the student) is trained to imitate the large one. The cost is that the student usually cannot reach the teacher’s ceiling, but inference cost can drop by an order of magnitude. The Qwen 2.5 series and the Phi series use distillation heavily.

Practical guidance [25]: “If the product needs extremely low latency and the highest accuracy, do a full fine-tune; if you need fast experiments, many variants, and a separate adapter per customer, use LoRA; if the model is large and VRAM is limited, use QLoRA.”

1.3 The inference stack and decoding strategies

Once the model is trained and online, “which strategy samples the next token from the logits” decides the character of the output:

  • Greedy / Argmax: always pick the token with the highest probability. The result is stable, but it easily falls into repetition (“the the the…”)
  • Beam Search: keep the top-K candidate sequences. It works well in machine translation, and it tends to sound mechanical in dialogue
  • Top-K Sampling: sample at random from the K tokens with the highest probability. K=40 is a common value
  • Top-P / Nucleus Sampling (Holtzman 2019): sample from the smallest set whose cumulative probability reaches P. P=0.9 is a common value, and it is more adaptive than top-K
  • Temperature: divide the logits by a temperature T, then apply softmax. T<1 leans conservative (close to greedy), T>1 leans divergent, and T=0 is equivalent to greedy
  • Repetition Penalty / Frequency Penalty / Presence Penalty: suppress repeated tokens

The de facto standard in engineering today is temperature=0.7 + top_p=0.95 (the default at OpenAI / Anthropic). For creative generation, raise T. For strict JSON extraction, set T=0 and pair it with grammar-guided generation (such as Outlines, Guidance, and the GBNF of Llama.cpp).

1.4 The classic techniques of prompt engineering

The “classic era” of prompt engineering can basically be covered by a single technique map [28][29][30]:

1. Zero-shot / few-shot (Zero-shot / Few-shot)

Asking directly, versus giving a few examples. The GPT-3 paper by Brown et al. in 2020 found that few-shot can let a small model approach the level of a larger model after fine-tuning — this is the birth of the idea of in-context learning. In 2026, few-shot is still the strongest baseline for 80% of tasks [29].

2. Chain-of-Thought (CoT)

Proposed by Wei et al. in 2022. Have the model write the “process of thinking” before it writes the answer, which sharply raises accuracy on math and reasoning tasks. The simple trigger phrase “Let’s think step by step.” lifts accuracy on GSM8K from 17% to 78% [28]. The core mechanism of CoT: complex reasoning that would otherwise have to be finished in a single forward pass is spread across the generation of many tokens, which is equivalent to dynamically expanding the amount of computation.

3. Self-Consistency

Wang et al., 2022. Sample the same CoT prompt N times (at a high temperature), then vote for the answer that appears most often. On math and programming it lifts CoT by another 5-10 percentage points, at a cost of N times the tokens.

4. ReAct (Reasoning + Acting)

Yao et al., 2022 [4]. It interleaves thinking (Thought) and acting (Action): the model first thinks “what should I look up now,” then calls a tool (search / a calculator / an API), observes the result (Observation), and then goes on to think about the next step. On the ALFWorld interactive tasks its absolute success rate is 34% higher than imitation learning + RL, and on WebShop it is 10% higher. ReAct is the ancestor of every later agent architecture — the react agent template in LangGraph, the conversable agent in AutoGen, and the task agent in CrewAI are all, in essence, engineered variants of ReAct.

5. Tree of Thoughts (ToT) / Graph of Thoughts (GoT)

Yao 2023 / Besta 2023. CoT is a single chain of thought. ToT expands each step into several branches and searches the whole reasoning tree with BFS/DFS plus heuristic scores. GoT goes further and generalizes the tree to a DAG, allowing nodes to merge (“these two lines of thought of mine actually point at the same answer”). The cost is several times to ten times the tokens, and it pays off only on tasks such as math reasoning and planning, where the answer is sparse but the paths are many.

6. Self-Refine

Madaan et al., NeurIPS 2023 [3]. The same model plays three roles: generator (draft) → critic (judge itself) → reviser (rewrite). An average gain of 20% across 7 tasks (verified on both GPT-3.5 and GPT-4). This is the prototype of later “self-improvement” lines such as Reflexion, CRITIC, and Constitutional AI.

7. Reflexion

Shinn et al., 2023. Self-Refine is self-improvement within a single round. Reflexion writes the self-reflection into “long-term memory” — if a task fails, the cause of the failure is summarized as a reflection and attached to the prompt of the next task of the same kind. It is equivalent to letting the agent learn from experience.

8. Prompt Chaining / Decomposition

A complex task is split into a multi-step prompt, and the output of each step is fed to the next (the “workflow” pattern). LangChain, LlamaIndex, and Semantic Kernel use this pattern heavily. The advantage is that it is debuggable and observable. The disadvantage is that information can be lost between steps.

9. Role Prompting / System Prompt

“You are an expert Python developer. …” injects an identity and a setting into the model. The Claude series generally follows the system prompt more closely than the GPT series, so the community consensus is that “Claude prompt engineering leans toward XML tags plus a strong system prompt” [29].

10. Differentiation by model

By 2026, prompt engineering has already split from “universal best practice” into “model-specific best practice” [29][30]:

  • Claude (Anthropic): prefers XML tags (<context>...</context>, <instructions>...</instructions>), a long system prompt, and, for a multi-step reasoning task, saying “think step by step” directly
  • The GPT series (OpenAI): prefers a concise JSON schema, structured function calling, and is friendly to Markdown
  • Gemini: natively multimodal, and it supports a mixed image-plus-text prompt best
  • DeepSeek-R1 / o1 / reasoning models: do not add a CoT trigger on top (the model already has one). Give the question directly, and keep the temperature on the low side

1.5 Automatic and advanced prompts

Writing prompts by hand has a ceiling. From 2023 a direction emerged: “let the LLM write the prompt itself.”

  • APE (Automatic Prompt Engineer) (Zhou 2023): one LLM generates candidate prompts, they are scored on a dev set, and the best is selected by iteration
  • OPRO (Optimization by PROmpting) (Yang 2023, Google): treats prompt optimization as a meta-optimization problem and lets the LLM itself serve as the “optimizer,” proposing a new prompt each round from the previous round’s prompt plus its score
  • Promptbreeder (Fernando 2023, DeepMind): APE plus an evolutionary algorithm, so that prompts mutate, are selected, and cross over inside a population
  • DSPy (Stanford 2023): treats the prompt as a layer of a neural network, and uses a compiler plus bootstrapped few-shot examples to generate the best demo samples automatically, so that you write “modules” rather than prompts

In 2025-2026 DSPy entered the mainstream — it was taken up by Databricks, Snowflake, and others as an internal prompt-compilation framework. It marks an important turn: a prompt is no longer a handwritten art; it is a product of compilation.

1.6 Evaluation, red teaming, and the “twilight” of prompt engineering

The success of prompt engineering has to be measurable. Promptfoo [29] is the de facto standard among open-source prompt-testing frameworks — define test cases, run comparisons across models, and integrate with CI. A minimum viable test set: 20 diverse cases (happy path + edge case + adversarial), run automatically after every prompt change.

Prompt engineering has three classes of failure mode: - Hallucination: the model fabricates facts with a straight face - Prompt injection: the user input smuggles in “ignore all the instructions above and do X instead,” and hijacks the system prompt - Jailbreak: bypass the alignment so the model emits harmful content (“DAN,” role-play, long-tail language attacks, and so on)

By 2026 OWASP has made the Top 10 for LLM Applications the standard taxonomy. The top three are LLM01 Prompt Injection, LLM02 Insecure Output Handling, and LLM03 Training Data Poisoning [36]. These problems cannot be solved by “writing a better prompt.” They require guardrails (see §3.3.7 in Part III).

From the second half of 2024, the argument over “whether prompt engineering still matters” began to surface. In the YC AI School talk Software Is Changing (Again), Karpathy pointed the industry’s focus at the next stop — context engineering.

Part II: Context Engineering

2.1 Definition and origin

The phrase “Context Engineering” began to circulate in the community in the second half of 2024, and it is generally credited to Karpathy’s YC AI School talk Software Is Changing (Again) [5]. The definition he gave has been quoted again and again since:

“In every industrial-strength LLM app, context engineering is the delicate art and science of filling the context window with just the right information for the next step.” (In every industrial-grade LLM application, context engineering is the delicate art and science of filling the context window with exactly the right information, in preparation for the next step of inference.)

In the 2025 official article Effective Context Engineering for AI Agents [6], Anthropic goes further and positions it as “the natural evolution of prompt engineering”: “What prompt engineering cares about is the sentence you say to the model; what context engineering cares about is all the information the model can see at the moment of inference — the system prompt, the conversation history, the tool definitions, the retrieved documents, the memory, the planning state, the constraints, and the policy.”

In the blog post Context Engineering for Agents [7], the LangChain team gives an engineering definition that is often cited:

“Context engineering is the discipline of designing dynamic systems that, at the right time and in the right format, provide the LLM with the right information and the right tools, so that the model has everything it needs to finish the task.”

Why is “prompt engineering” no longer enough? Three fundamental changes:

  1. The window grew. It rose all the way from GPT-3.5’s 4K to Gemini 2.5 Pro’s 1M and Claude Opus 4.7’s 1M (with 1M context mode enabled). What can be put into the window went from “a few paragraphs” to “an entire book.” Deciding what to put in became much more important than writing that one sentence well.
  2. Agents rose. A single-turn prompt is an isolated transaction. An agent is a persistent state machine. The context of every step of inference comes from the previous step’s output + tool returns + retrieval + memory. The “prompt” is no longer the sentence the user wrote. It is something the agent framework assembles dynamically.
  3. Multimodal input plus tool calling. Context is no longer only text. It also includes images, tables, code, tool schemas, retrieved chunks, structured memory, and a scratchpad. Organizing this heterogeneous information well is an engineering problem.

By early 2026, the industry consensus is this: the core difficulty of a production-grade LLM application has moved from “writing the prompt” to “managing the context” — Anthropic says directly in its documentation that “Context Engineering is the key discipline for building reliable AI agents” [6].

2.2 The physics of long context

To understand why “stuffing the window full” is a bad idea, you first have to understand three physical constraints on context:

Constraint one: O(N²) cost

Back to §1.1 in Part I: standard attention is N² in complexity. Take the context from 32K to 128K and the attention compute is 16×, not 4×. For an inference service this means two things: (a) time to first token (TTFT) rises, because the whole prompt has to be prefilled first; (b) VRAM is filled by the KV cache, and concurrency falls.

Constraint two: KV-cache VRAM

At inference time, every attention layer has to keep a cache of K and V (to avoid recomputation). For a 70B model at a context of 128K, the KV cache can occupy 40+ GB, larger than the model weights themselves. This is why techniques that “manage the KV cache,” such as vLLM’s PagedAttention [10] and SGLang’s RadixAttention [11], became the core competitive advantage of inference servers (see §3.3.4 in Part III).

Constraint three: Lost-in-the-Middle

The 2024 TACL paper by Liu et al., Lost in the Middle: How Language Models Use Long Contexts [2], systematically verified a counterintuitive phenomenon: put the key information at the start or the end of the prompt and the model uses it well; put it in the middle and the model often looks right past it. Recall versus position is a U-shaped curve — the start has a primacy bias, the end has a recency bias, and the middle is a black hole.

The curve has been verified on GPT-3.5, GPT-4, and Claude alike. Even Gemini 1.5 Pro in 2025 can reach 99.7% recall on a simple needle-in-a-haystack test, but when the task becomes “find 8 relevant facts inside 1M tokens and synthesize them,” average recall drops to ~60% [41].

2.3 RULER and the real ability of a 1M context

The RULER benchmark [12] published in 2024 by NVIDIA and other institutions (What’s the Real Context Size of Your Long-Context Language Models?) upgrades “long-context ability” from the toy needle-in-a-haystack test to a torture suite:

  • Needles of many kinds and many counts: not one buried fact, but many buried facts of different types
  • Multi-hop reasoning: you can find B only after you find A
  • Aggregation tasks: count a total, or take an average, inside a long document
  • Variable tracking: follow a variable through many reassignments across a span of 100K tokens

The truth RULER exposes: almost every model that claims a context of 100K+ has an “effective context” on RULER far smaller than the value it claims. For example, some model claims to support 200K, but on RULER accuracy falls below 80% past 50K, and at 128K it is already close to random.

This pulled the industry back to reality: long context is not a replacement for RAG. It is a complement.

Long context vs. RAG: a decision framework

In Long-Context Models vs RAG: When the 1M-Token Window Is the Wrong Tool [41], Tianpan gives a decision framework that is mainstream in 2026:

Dimension 1M-context model RAG
Latency 30-60× slower (the whole window must be prefilled) Two stages, retrieval plus generation, but the generation-stage input is small
Cost per query ~1250× more expensive Retrieval is nearly free; generation cost follows the number of relevant chunks
Data updates Every query has to retransmit Update the index once, and every query benefits
Explainability A black box Retrieval results can be audited and cited
Multi-fact recall ~60% (in practice) With a reranker, 90%+ is reachable
Scenarios that truly fit long context A one-shot deep analysis (“read this 200-page PDF and summarize the insights”) Knowledge-base question answering, customer support, document retrieval

Practical guidance: 90% of “knowledge retrieval” scenarios should use RAG, and only 10%, the “deep analysis of a single document,” should use long context.

2.4 Full-stack RAG selection

RAG (Retrieval-Augmented Generation) is the most mature branch of context engineering, and it has already evolved into a complete sub-discipline. The state of 2025-2026 can be summed up as a four-generation evolution [43]:

Generation one: Naive RAG (2020-2022) Retrieve → concatenate → generate. chunk + embed + vector search + LLM. Simple, but brittle: cut the chunks wrong and everything is wrong; if retrieval recall is low, the answer is wrong.

Generation two: Advanced RAG (2023-2024) Introduces query rewriting / reranking / hybrid search / metadata filters. Recall was pulled from 50% up to 80%.

Generation three: Modular RAG (2024) Splits RAG into composable modules: indexing / pre-retrieval / retrieval / post-retrieval / generation, each of which can be replaced on its own. The engineered RAG abstractions of LangChain and LlamaIndex.

Generation four: Agentic RAG (2025-2026) Treats RAG as one of an agent’s capabilities, and lets the agent decide on its own when to retrieve, what to retrieve, how to judge the retrieved results, and whether to retrieve again [43]. Self-RAG / CRAG / Agentic RAG are the representatives of this generation.

What follows takes apart the choice space of 2026 in the order of the RAG pipeline.

2.4.1 Document parsing (Parsing & Layout)

Documents in the real world are PDFs, PPTs, scans, Excel, and HTML, not plain text. This step is often skipped, and its effect is very large:

  • Basic: pypdf / pdfplumber (fast, but tables and multi-column layout go wrong easily)
  • Advanced: unstructured / LlamaParse (with a layout model that can recognize headings / paragraphs / tables / lists)
  • OCR: PaddleOCR / Tesseract / EasyOCR (scans, images)
  • Natively multimodal: use GPT-4o / Gemini / Claude to read the PDF page directly (vision). It fits documents whose layout is extremely complex, but the cost is high
  • Dedicated commercial products: Azure Document Intelligence, AWS Textract, Microsoft MarkItDown

Best practice: run at least two parsers and compare them, then decide which to use. Tables and formulas must be handled specially (convert them to Markdown / LaTeX).

2.4.2 Chunking strategies (Chunking)

The chunking strategy affects recall quality far more than the choice of embedding model does:

  • Fixed Size Chunking: a fixed N tokens. The simplest. The problem: it easily cuts semantic units apart
  • Recursive Character Splitting: cut recursively down the levels paragraph → sentence → word. The LangChain default. A baseline with a good cost-to-quality ratio
  • Semantic Chunking: use embeddings to compute the similarity of adjacent sentences, and cut where the similarity drops sharply
  • Document-Specific: cut Markdown by heading, code by function, and HTML by DOM
  • Agentic Chunking: let an LLM read the document and decide for itself how to cut it. The most expensive, and the most accurate
  • Late Chunking (Jina 2024): embed the whole document first to get token-level embeddings, then chunk and aggregate. In long-context settings, recall is 10-15% higher than traditional chunking

General advice: a chunk size of 256-512 tokens and an overlap of 50-100 tokens is the sweet spot for most tasks.

2.4.5 Retrieval: sparse + dense + late interaction

Vector retrieval (dense) is good at semantic similarity and poor at exact keyword matching (product IDs, proper nouns, tolerance for typos). Production-grade RAG is almost always hybrid search:

  • Sparse: BM25 / SPLADE / BGE-sparse (keywords + term frequency)
  • Dense: embedding-based vector search (semantics)
  • Late interaction: ColBERT / ColBERT-v2. Each token has its own embedding, and at retrieval time the scores are aggregated by token-level max-similarity. Recall is higher than single-vector dense retrieval, but the index is 100x larger. Vespa and Qdrant already support it

The mixing strategy: merge the sparse and dense result lists with RRF (Reciprocal Rank Fusion). It is simple, and it needs no tuning.

Empirical result: hybrid search + a reranker gains +9.3 percentage points of MRR over semantic-only, and with Cohere Rerank accuracy can reach 90%+ [as measured in the LanceDB benchmark].

2.4.6 Reranking (Reranker)

After first-stage retrieval (embedding / BM25) has recalled the top 100, a cross-encoder that is more expensive and more accurate reranks the query-document pairs, and the top 5 go to the LLM. The ROI of this step is extremely high [a reranker survey]:

2.4.7 Query rewriting (Query Rewriting / Expansion)

The user’s “今天天气咋样” and the document’s “current weather conditions” mean the same thing, but the vocabularies do not overlap. Query rewriting processes the query before retrieval:

  • HyDE (Hypothetical Document Embeddings): first have the LLM imagine “what an answer document would write if one existed,” and retrieve with that imagined text (not with the original query). The recall gain is clear in specialized domains
  • Multi-Query: have the LLM rewrite the original query as 3-5 different phrasings, retrieve with each, and then merge
  • Step-Back Prompting: first abstract the query into a broader question (“What is the specific number in company X’s Q3 earnings report?” → “What is the overview of company X’s Q3 earnings report?”), and use the retrieval results of the abstract question as the setup
  • Sub-Query Decomposition: split a compound question into several sub-questions and retrieve each one (“compare A and B” → [“traits of A”, “traits of B”])
  • The combination of HyDE + Multi-Query is one of the strongest baselines today on retrieval benchmarks such as BEIR

2.4.8 GraphRAG

Microsoft GraphRAG (open-sourced in 2024) and community variants such as LightRAG / Nano-GraphRAG extend retrieval from “vector similarity” to “knowledge-graph traversal”:

  • Build phase: use an LLM to extract the entities and relations in the documents, and build a knowledge graph
  • Retrieval phase: map the query onto entities in the graph, and do a local subgraph query plus a summary
  • Advantage: it can answer “topic-level” questions (“what compliance risks are there across all of our supplier contracts”). Classic RAG fails on this kind of question because there is no locally similar chunk [43]
  • Cost: building the graph is very expensive (an LLM extracts entities from every passage), so it suits a static, high-value knowledge base

In some settings GraphRAG pushes retrieval precision to 99% (relationship-dense domains such as financial compliance, law, and medicine) [43].

2.4.9 Self-RAG / CRAG / Agentic RAG

Self-RAG (Asai 2023): while generating, the model decides for itself when to retrieve, evaluates whether the retrieved results are relevant, and critiques whether its own output is supported. CRAG (Corrective RAG): after retrieval, each chunk is labeled with a “high / medium / low confidence” tag, and low confidence triggers a web search as the fallback. Agentic RAG: packs all of the abilities above into an agent loop, and the agent cycles through “think → retrieve → judge → rewrite the query → retrieve again → synthesize” until it is confident. LangGraph is the mainstream framework for implementing Agentic RAG [Vinod Rane 2026].

Empirical result: in production deployments, Self-RAG can reduce “unnecessary retrieval” by 25-40% [43], because the model has learned not to retrieve for things already in its own knowledge.

2.4.10 Multimodal RAG

Indexing schemes that mix images and text:

  • Late fusion: embed text and images separately; at retrieval time, retrieve separately and then merge
  • Early fusion: use a multimodal embedding such as CLIP / Gemini Embedding, and embed images and text into the same space
  • VLM-as-extractor: use GPT-4o / Claude 3.5 Sonnet to turn images into detailed descriptions, then run text RAG (the highest cost, but the most stable recall)

2.5 Memory systems

If RAG solves “how a knowledge base gets into the context,” a memory system solves “how the agent’s own experience gets into the context.”

2.5.1 The three axes of memory

A classification borrowed from cognitive psychology:

  • Short-term memory (Working Memory): what is inside the current conversation window (the system prompt + the most recent N turns)
  • Long-term memory, further split into three kinds:
    • Episodic memory: “last Wednesday we discussed X”; “last time, the user said they were not familiar with React”
    • Semantic memory: “the user’s native language is Chinese”; “the user prefers a dark theme”; “the project uses PostgreSQL”
    • Procedural memory: “this kind of task is usually done as the steps X→Y→Z”; “on a timeout, retry 3 times first”

2.5.2 Four memory systems compared (2026)

System Core architecture Strength Suited to
Mem0 Vector + optional graph; three layers of user / session / agent The simplest to integrate, and the documentation is solid Adding memory to a general chatbot
Letta (formerly MemGPT) OS-inspired; the agent manages memory blocks itself through tool calls Explicit and explainable; the agent has a persistent identity Agents that run for a long time (days/weeks)
Zep A temporal knowledge graph; tracks how facts change over time Strong temporal reasoning, enterprise-grade Settings where user state changes (CRM/customer support)
Anthropic Memory Tool A hosted store + automatic injection + an API to revise/delete Native integration with Claude Inside the Anthropic ecosystem

Observations across the architectures:

Mem0 [the Mem0 paper, arXiv 2504.19413] is the easiest scheme to wire in. Three steps: extract a “memory” from the interaction → store it (vector by default) → on a later query, retrieve it and inject it into the prompt. The three-layer hierarchy of “user / session / agent” makes multi-tenant isolation happen automatically.

Letta has a distinctive design philosophy: it treats memory as the agent’s “editable state,” and the agent itself uses tool calls to read / write / search its own memory blocks. That is equivalent to giving the agent an OS-style memory manager. The advantage is that the agent can keep an “identity” across sessions — the next time it starts, the memory blocks are still there.

What sets Zep apart is that it is temporal — the same fact, “the user’s job,” may go from “at Google” → “at Anthropic” → “starting a company.” Zep records the time dimension in a knowledge graph, so both “what is the user’s job now” and “what was the user’s job last year” come out correct.

Anthropic Memory Tool is the official memory interface launched in the second half of 2025 alongside Claude Sonnet 4.6: declare use of the memory tool on the API call, and the model decides on its own what memory to write and which memories to read. The developer only handles the business logic.

Practical selection [the n1n.ai 2026 comparison]: - A simple chatbot plus memory → Mem0 - An agent that has to run on its own across days → Letta - Enterprise, and user state changes → Zep - Already bound to Anthropic → Memory Tool

2.5.3 Common traps in memory

  • Memory explosion: remember everything → noise drowns the signal → retrieval quality falls. Active forgetting / summarization / priority eviction is required
  • Stale memory: last week the user said “I like cold coffee,” and today they tell the model “I only drink hot coffee now.” A temporal system such as Zep is made for exactly this
  • Cross-user leakage: a multi-tenant SaaS must isolate strictly by user_id

2.6 Context-management strategies

Even with RAG and memory, “what to put in, how much to put in, and when to put it in” when filling the context window is still a hard problem. The Anthropic article [6] gives a few principles:

  1. Not all information is equally important — rank it by priority, and put the most important material at the head and the tail (stay out of lost-in-the-middle)
  2. Dynamic trimming — when the context nears the limit, actively summarize the early conversation and evict stale tool results
  3. A /compact mode — products such as Claude Code support a /compact command, which compresses the current long conversation into a summary plus the key facts, keeping the meaning while reclaiming tokens
  4. Separate the scratchpad from working memory — manage the agent’s “scratch paper” (the reasoning process, intermediate tool results) separately from the “outward-facing context,” so that it does not get contaminated

2.7 The MCP / A2A protocol ecosystem

Wiring tools and data sources into an LLM was dirty work for a long time — every LLM’s function-calling schema is different, and every tool has to have a hand-written wrapper. MCP (Model Context Protocol) [9] is an open standard released by Anthropic in November 2024. The goal is to be the “USB-C” of AI — one protocol that lets any LLM connect to any tool or data source.

The key design of MCP: - JSON-RPC 2.0 as the transport protocol - A server / client architecture: an MCP server wraps an external system (PostgreSQL, GitHub, a file system, a custom API) and exposes three classes of primitive: tools (callable functions), resources (read-only data), and prompts (templates) - Decouple the tool from the LLM: function calling hard-wires the tool definition to the LLM provider. MCP lets the tool and the LLM evolve independently

The timeline: - 2024-11: Anthropic releases it - The first half of 2025: OpenAI / Google / Microsoft / Amazon add support in succession - 2025-12: Anthropic donates MCP to the Agentic AI Foundation (AAIF) under the Linux Foundation, jointly governed with Block and OpenAI - 2026-02: monthly downloads of the Python + TypeScript SDKs break through 97 million [9]

A2A (Agent-to-Agent) is another class of protocol. It is concerned with how agents collaborate with each other (task delegation, shared state, workflow orchestration). MCP and A2A are complementary:

“MCP gives an agent a pair of hands (connecting tools and data). A2A lets several agents work as a team. MCP is vertical integration. A2A is horizontal collaboration.”

By the spring of 2026, MCP has become the de facto standard of the agent ecosystem. A2A is still in a phase of competition among several protocols (Google A2A / Microsoft’s AutoGen protocol / Anthropic’s Agent Skills, and others, are all trying).

Part III: Harness Engineering

3.1 Origin: “that layer of stuff,” now named

“Harness Engineering,” as a term, was formally named in February 2026 by Mitchell Hashimoto (founder of HashiCorp) [8]. The triggering event was an article by OpenAI engineer Ryan Lopopolo describing OpenAI’s internal agent infrastructure. After reading it, Hashimoto said: “This is harness engineering — all the scaffolding, constraints, and feedback loops around an agent that let it actually work.”

Karpathy laid the groundwork for this concept from another angle. Across 2025-2026 he described, more than once, that his own coding workflow had flipped from “mostly write the code by hand, and occasionally let an agent help” to “mostly let the agent write the code, and touch it up by hand myself.” What makes this way of working possible is not that the model got stronger. It is the environment around the agent — the repo structure, the CI configuration, the formatter, the package manager, the framework constraints, the project instructions, the external tool integrations, the linter — and together these make up the agent’s “harness.”

In the April 2026 Medium article Agent Harness Engineering: The Rise of the AI Control Plane [32], Adnan Masood sums it up: “Harness Engineering is the building of that whole system which governs a deployed AI agent across many interactions — guides, sensors, data context pipelines, eval suites, constraint enforcement.”

The core idea of harness engineering is stated again and again:

Every time an agent makes a mistake, do not merely hope it does better next time. Engineer the environment so that it cannot make the same mistake in the same way again.

This unifies “AI safety” and “AI engineering” under one principle: constrain the environment, rather than the model itself. A model’s “capability” is variable (a new generation every three months), but environmental constraints are stable, and they accumulate.

3.2 The boundary with prompt engineering and context engineering

A clean division of the three layers of abstraction:

Layer Concern Unit Time scale
Prompt Engineering How this one sentence is written Characters / sentences A single LLM call
Context Engineering What the model sees at this moment of inference A set of tokens A single inference (including RAG, memory, tool schemas, and so on)
Harness Engineering What environment the agent runs in, and how it stops making the same mistake The system / the process Across many interactions, evolving continuously

An analogy: - prompt = one specific instruction you give an employee - context = all the material the employee can see on the desk (a notebook, email, documents, chat history) - harness = the company’s whole set of rules, tools, CI process, code review, and coaching system

3.3 The seven components of the harness layer

What follows takes apart the seven core components of a production-grade agent harness in 2026.

3.3.1 The tool-integration layer (Tool Integration)

See §2.7 on MCP / A2A. Beyond that:

  • Function Calling: native to the LLM provider (OpenAI, Anthropic, Google, and DeepSeek all support it). It fits simple tools and a single-LLM-provider setting
  • MCP: cross-LLM, reusable, and the ecosystem is exploding (97M monthly downloads)
  • An OpenAPI / GraphQL adapter: wrap any REST/GraphQL service as an MCP server
  • Agent Skills (introduced by Anthropic in 2026): package “the agent knows how to do a certain class of task” as a reusable unit

In practice: MCP is already the de facto standard of 2026. New projects go straight to MCP, and existing projects stay compatible through an MCP adapter.

3.3.2 Sandbox and code execution (Sandbox)

When an agent writes code, runs commands, or handles files a user uploaded, it has to do so inside an isolated environment. Otherwise, the moment prompt injection arrives, the agent uploads ~/.ssh/ from your server to the public internet.

  • E2B: available as both open source and SaaS. A secure sandbox runs arbitrary Python / Node / Bash, with a millisecond-scale cold start
  • Daytona: an open-source dev environment, originally aimed at dev containers, with agent-sandbox support added from 2025
  • Modal: serves as both a serverless GPU and a sandbox
  • OpenAI Code Interpreter (Apps SDK): hosted, and simple
  • Anthropic’s Claude Computer Use: lets Claude operate desktop applications. In essence it is a more aggressive sandbox

The minimum bar: never eval() agent output inside the main process of a production server. Even something that looks harmless, such as os.path.join.

3.3.3 The LLM gateway (LLM Gateway)

Pull “calling an LLM” out of your business code into an independent gateway layer, and handle, in one place, routing, fallback, caching, rate limits, billing, observation, and key management. The mainstream options in 2026 [37][38]:

Gateway Mode Headline capability Suited to
LiteLLM An open-source Python proxy A unified OpenAI-compatible interface for 100+ LLMs, self-hosted Small and mid-size teams; a preference for self-hosting
Portkey Commercial + self-hosted Semantic cache, guardrails, enterprise-grade observation Enterprise production
OpenRouter A SaaS marketplace One API key for 200+ models, pay as you go Startups / prototypes
Helicone AI Gateway Open source + SaaS High performance implemented in Rust, health-aware routing + circuit breaking, native observation High-concurrency production
Cloudflare AI Gateway SaaS (at the edge) A global edge cache, zero operations Already on the Cloudflare stack

The key capabilities:

  • Multi-provider routing: pick a provider dynamically by cost / latency / model capability. If GPT-4 fails, fall back to Claude, then fall back to Llama.
  • Semantic cache: the signature advantage of Portkey and Cloudflare — not a literal match, but “a semantically similar query reuses the cached response.” Customer-support and knowledge-base settings can reach a cache hit rate of 60%+.
  • Circuit breaking: Helicone’s “health-aware routing + circuit breaking” automatically isolates the failing endpoint when a provider fails.
  • Unified billing + quotas: quotas by user_id / org_id, so that a malicious user cannot burn through the allowance.
  • Key management: business code never touches the API key. It all stays in the gateway.

Note [37]: in 2026 the LLM-proxy ecosystem had two major events — Helicone was acquired, and LiteLLM was found to have a supply-chain problem in its dependencies. “Running a third-party proxy in a production environment” is itself a security decision. The enterprise-grade recommendation is to self-host and pin the version.

3.3.4 The inference server (Inference Server)

If you self-host a model (an open-source 7B-70B, or one you trained yourself), the inference server decides throughput and cost. The state of 2026 [39][40]:

  • TGI (Text Generation Inference, HuggingFace): from December 2025 it entered maintenance mode. HF officially recommends vLLM or SGLang for new deployments.
  • vLLM (UC Berkeley Sky Lab): the core innovation is PagedAttention [10]. It cuts the KV cache into pages of 16 tokens and manages them in a way similar to operating-system virtual memory, with VRAM fragmentation <4%. This raises, by several times, the concurrency a single card can run. The widest ecosystem (the default choice for HuggingFace, the cloud vendors, and enterprise self-hosting). It supports prefix caching (automatically detect a shared prefix and reuse the KV) and speculative decoding (a small model guesses first and the large model verifies; a 1.3-2x speedup when the acceptance rate is ≥0.7).
  • SGLang (LMSYS): the core innovation is RadixAttention [11] — a radix-tree data structure automatically discovers and reuses the KV cache, with no need to configure prefix caching by hand. On multi-turn conversation and agent workloads (dynamic context shared across requests) it is 10-20% faster than vLLM; on a prefix-heavy workload it is up to 6.4x faster than the baseline. On small models (7B-13B), SGLang’s throughput is ~29% higher than vLLM’s; at the 70B scale the gap narrows to 3-5%.
  • NVIDIA Triton Inference Server: the traditional choice. People still use it for mixed multimodal / multi-model workloads, but for pure LLM inference it no longer has much of an advantage.
  • LMCache (proposed in 2025): as an independent KV-cache layer, it can share cache across different inference-server instances. In an enterprise multi-replica deployment it can save a further 30-50% of VRAM.

Selection experience: pure-text LLM inference → SGLang (multi-turn / agent workloads) or vLLM (general / simple single-turn); mixed multimodal → vLLM or Triton.

Many teams end up with “a combination of two tools”: an OSS platform (Langfuse / Phoenix) for development and the dashboard, and a proxy gateway (Helicone) for observing production traffic.

3.3.6 Evaluation (Evaluation)

An LLM application does not have the hard constraint of a traditional unit test, where input X must produce output Y. The core question of evaluation is “is the model’s answer a good answer,” and that splits into two kinds [35]:

  • Offline evaluation (Offline Eval): run a fixed dataset, and score with a metric / LLM-as-judge / a human
  • Online evaluation (Online Eval): sample and score inside production traffic, and monitor quality drift

The mainstream frameworks in 2026 [35]:

LLM-as-Judge has been the core paradigm since 2024: a stronger LLM (usually GPT-4 / Claude Opus) scores the agent’s output. The points that matter: the judge model must be stronger than the model under test; the prompt has to state the rubric clearly; the judge has bias of its own (a bias toward models from its own family, a bias toward long answers).

In practice [35]: “You almost certainly need two tools — a lightweight framework (DeepEval / RAGAS / Promptfoo) for CI/CD gating, and a platform (Braintrust / LangSmith / Arize) for human labeling, regression tracking, and the stakeholder dashboard.”

3.3.7 Guardrails (Guardrails)

An LLM is an untrusted component. It will hallucinate, it will be injected, it will leak secrets, and it will generate harmful content. Guardrails are a “filter layer” placed on both the input side and the output side of the LLM. The mainstream in 2026:

  • NVIDIA NeMo Guardrails [36]: open source. It describes dialogue flow and constraints in the Colang DSL. It supports 5 kinds of rails:
    • Input rails (the user-input side)
    • Dialog rails (constraints on the dialogue flow)
    • Retrieval rails (filtering of RAG chunks)
    • Execution rails (wrapping of custom actions)
    • Output rails (the LLM-output side) Integrated with the NVIDIA Nemotron Safety model (content safety, PII, and jailbreak detection).
  • Guardrails AI (open source): Pydantic-style “validators,” checking that the LLM output conforms to a schema, contains no PII, and contains no jailbreak trigger words
  • AWS Bedrock Guardrails: hosted guardrails, with zero integration work in the AWS ecosystem
  • Azure Content Safety: the same, for the Azure ecosystem
  • Lakera Guard: commercial, specialized in prompt-injection detection
  • Protect AI Layer: a commercial full-stack security platform

Compliance is the driver: the high-risk obligations of the EU AI Act take effect on 2 August 2026 [36], and they place mandatory guardrail requirements on AI systems in settings such as medicine, education, hiring, finance, and critical infrastructure. The OWASP Top 10 for LLM Applications has become the industry-standard risk classification.

A practical configuration [Atlan 2026]: - Input side: prompt-injection detection + PII filtering + a topic allowlist - Retrieval side: grade retrieval results by sensitivity, and do not let sensitive content enter the LLM - Output side: detection of PII / sensitive terms, factuality verification, JSON schema validation, length / rate limits - Audit side: record every request “blocked by the guardrails,” and review them on a schedule

3.4 Agent orchestration frameworks

Assembling the components above into “one agent” takes an orchestration framework. The mainstream in 2026:

  • LangGraph (LangChain): a state machine based on a graph (DAG), with explicit nodes and edges, a checkpointer built in, and human-in-the-loop as a first-class citizen. The widest ecosystem, and it is the de facto standard
  • AutoGen (Microsoft): a multi-agent dialogue framework. Agents negotiate with each other in natural language
  • CrewAI: a “role + task” abstraction. Team agents do the collaboration
  • LlamaIndex Agent: an agent framework that is RAG-first
  • Semantic Kernel (Microsoft): leans toward the .NET ecosystem

Synthesis & Insights: the full picture of the three-layer evolution

The timeline narrative

Lay the industry’s focus over the past four years out as a timeline:

  • 2022-2023: the era of prompt engineering
    • ChatGPT set off the boom, and everyone was writing prompts
    • Main techniques: CoT, few-shot, ReAct
    • Engineering artifacts: prompt templates, prompt libraries, prompt training courses
    • Metaphor: “the person who can talk to the model”
  • 2024: context engineering rises
    • Named by Karpathy, and pushed forward by Anthropic
    • Long context (100K → 1M) + RAG maturing + memory systems emerging
    • Main techniques: RAG, vector stores, rerankers, MCP (November)
    • Engineering artifacts: vector-DB deployments, RAG pipelines, the MCP server ecosystem
    • Metaphor: “the person who can build a stage for the model”
  • 2025-2026: harness engineering becomes the key to production
    • Named by Hashimoto, OpenAI’s internal architecture made public, Karpathy’s workflow flipped
    • Main techniques: MCP (97M monthly downloads), inference servers (vLLM/SGLang), agent orchestration (LangGraph), observability, evaluation, guardrails
    • Engineering artifacts: a complete agent stack, compliance frameworks, an enterprise AI control plane
    • Metaphor: “the engineering manager who can tame a herd of agents”

How the three layers relate

They stack, rather than replace one another. A production-grade agent needs all three layers:

  • Fail to write the prompt well (layer 1) → the model does not understand the task
  • Fail to manage the context well (layer 2) → the model cannot see the information the task requires
  • Fail to build the harness well (layer 3) → in production the system is uncontrollable, unreliable, and unable to evolve

An analogy with software engineering: - prompt = the specific function you write - context = the data and the dependencies this function can reach while it runs - harness = the whole project’s CI / CD / monitoring / testing / release process

The migration of the engineer’s skill stack

In 2022, the most valuable skill of an LLM engineer was “the prompt intuition that can elicit the model’s best output.” In 2024, the most valuable skill was “standing up a RAG system so that every document in the company can be queried.” In 2026, the most valuable skill is “standing up an agent harness so that several agents run 7×24 in production without a major accident.”

Note that this line of migration is not the end. The next stop is very likely “the protocol engineer who can federate several agent harnesses” — the era when the A2A protocol ecosystem matures and agents from many companies interoperate.

Seven principles shared across the three layers

Whether it is the prompt, the context, or the harness, engineering practice follows a few shared principles:

  1. Measure before you optimize: with no eval data, no dashboard, and no baseline, every “improvement” is a hallucination
  2. Simplicity first: a baseline is enough for 80% of tasks; add complexity only where the baseline fails
  3. Observability above all: the trio of trace, log, and metric is the oxygen of a production agent
  4. Defensive programming: assume the model will hallucinate, will be injected, will time out, and will lose the network
  5. Reversible design: every step can be rolled back, and every component can be swapped out
  6. Cost awareness: every decision asks “how many tokens / how many USD / how many milliseconds does this step cost”
  7. Evolutionary iteration: start with the prompt → if that is not enough, add context → if that is not enough, add a harness. Do not build a complex stack from day 1

  7. What is particular to the Chinese setting. Chinese embedding / RAG / model selection differs from the English setting. Software engineering fundamentals

lint Software engineering — a static code checker that scans source for potential bugs and style problems

Analyze source without actually running it, and flag potential bugs, unused variables, style violations, and suspicious usage. Common tools:

  • JavaScript/TypeScript: ESLint, Biome
  • Python: Pylint, Ruff, Flake8
  • Go: golangci-lint
  • Rust: clippy
  • Shell: shellcheck

In agent engineering, lint is often used as a hard constraint in the harness — feeding lint errors back to the model to rewrite the code is much more reliable than merely saying “please follow the coding standards” in the prompt (Augment Code calls this a Constraint Harness).

type check / type checking Software engineering — check that the types of variables, parameters, and return values match

Make sure types are consistent across assignments and function calls:

  • Statically typed languages: TypeScript / Go / Rust / Java check at compile time
  • Dynamic languages plus annotations: Python uses mypy / pyright / Pyre; Ruby uses Sorbet

For an agent: after the agent finishes writing code, force a run of tsc --noEmit / mypy . / cargo check, and feed type errors back to the model to keep fixing. That is much more reliable than letting the agent “claim it checked the types” — a typical practice of harness engineering.

CI/CD Software engineering — continuous integration / continuous deployment pipelines

CI (Continuous Integration): on every commit, automatically run tests, builds, lint, type check, and other checks. CD (Continuous Deployment): after the checks pass, automatically deploy to test / staging / production.

Common tools: GitHub Actions, GitLab CI, Jenkins, CircleCI, Buildkite.

In agent engineering, CI is the most important deterministic feedback source — an LLM’s self-assessment is unreliable, but CI pass/fail is a 0/1 signal and can be used directly as ground truth. Hashimoto’s harness engineering stresses that whether a problem gets solved is strongly tied to whether the agent can verify its own work.

sandbox / sandbox Software engineering — an isolated code-execution environment that limits access to external resources

Run untrusted code (user uploads, LLM-generated code) in a restricted environment so it cannot damage the host. Isolation strength, from weak to strong:

  • Docker (runc): shared kernel, weak isolation, startup <1s
  • gVisor: user-space syscall interception, medium isolation
  • Firecracker / microVM: its own kernel, strong isolation, ~100–300ms cold start
  • E2B: Firecracker-based SaaS, the default choice for LLM agent code execution
  • Full VM: the strongest isolation, cold start on the order of seconds to minutes

An agent that runs user- or LLM-generated code must be sandboxed, with defense in depth on top: a network-egress allowlist + a read-only filesystem + time/memory quotas + no host credentials mounted.

canary / canary release Software engineering — send a small slice of traffic to the new version first, and roll out fully only after nothing looks wrong

The name comes from using canaries in coal mines to detect poison gas. A typical deploy sequence is: shadow (dual-run, do not return the result) → 1% → 5% → 25% → 50% → 100%, and each stage advances only if the core metrics show no regression.

For LLM applications, a new prompt / new model / new agent harness must go out through a canary. If any key metric (resolution rate, CSAT, refusal rate, p99 latency, cost per request) worsens past a threshold, roll back. The non-determinism of LLM applications makes canaries more important than they are for traditional software.

A/B test Software engineering — a controlled experiment that splits traffic into two groups, one on the old version and one on the new, and compares key metrics

Hash on user_id to split traffic so a given user always lands in the same bucket (avoiding a flickering experience). What to judge:

  • Business metrics: conversion rate, CSAT, retention — these test the hypothesis
  • Proxy metrics: thumbs up/down, refusal rate, number of conversation turns
  • Guardrail metric: cost and latency must not worsen past a threshold
  • Observation window: at least 1–2 weeks, covering a business cycle
  • Statistical significance: a t-test / Mann-Whitney test

Prompt changes, model swaps, and RAG changes in an LLM application should all go through an A/B test. Shipping on offline eval alone often fails in production (the live traffic distribution differs a lot from the gold set).

GMV / UV / CSAT / NPS / conversion rate Business metrics — the north-star metrics most often used in e-commerce / travel / customer support

The metrics the business side watches most closely when deciding whether an agent should launch:

  • GMV (Gross Merchandise Value): total value of merchandise sold, the core e-commerce metric. Daily GMV, monthly GMV, and incremental GMV (how much more the A/B treatment produced than the control) are all common ways of stating it.
  • UV (Unique Visitor) / DAU (Daily Active User): unique visitors / daily active users. UV measures traffic; DAU measures stickiness.
  • PV (Page View): page views, UV × views per person.
  • CTR (Click-Through Rate): the share of impressions that are clicked; a core metric for recommender systems.
  • Conversion rate: conversion at each step of the funnel — list page → detail page, detail page → order page, detail page → payment. In e-commerce / travel, +1pp is already significant, and +1.5–2pp counts as a large gain.
  • CSAT (Customer Satisfaction Score): a user satisfaction score (1–5 or 1–10). A customer-support agent must watch this.
  • NPS (Net Promoter Score): “how likely are you to recommend this to a friend”, from −100 to 100.
  • First-contact resolution rate / FCR (First Contact Resolution): the share of issues solved on the first interaction. A key metric for a customer-support agent.

What agent engineering watches: put model / prompt / RAG changes into an A/B test and look at these business metrics, not only offline benchmark scores. It is very common for a change to raise the benchmark while GMV / CSAT fall.

HITL / human-in-the-loop Software engineering — bring a human in to review or confirm at critical decision points

Pause an autonomous agent at a critical node and wait for a human:

  • Before high-risk actions: transfers, sending email, deleting data, merging a PR
  • When confidence is low: the model’s self-rated confidence is below a threshold
  • When regulation requires it: medical diagnosis, credit decisions, hiring screens (high-risk systems under the EU AI Act)

Design principle: “Humans steer. Agents execute.” (OpenAI Harness Engineering). An agent does not replace a person; it amplifies a person’s judgment — the person sets the plan, sets the constraints, and reviews the result, and the agent does the execution.

SLO / SLI / SLA / Error Budget Software engineering — the SRE quartet of “objective / indicator / contract / budget” for service quality

Four terms defined by Google’s SRE practice:

  • SLI (Service Level Indicator): an indicator — an observable number. For example “success rate 99.5%”, “p99 latency 280ms”, “task completion rate 92%”.
  • SLO (Service Level Objective): a target set on an SLI. For example “success-rate SLO = 99.9% (30-day sliding window)”. An internal commitment of the engineering team.
  • SLA (Service Level Agreement): a contract with the user or customer. Breaking it means paying money or refunding the service fee. It is usually looser than the SLO (SLO 99.9% → SLA 99.5%), leaving a buffer.
  • Error Budget: 1 - SLO. An SLO of 99.9% means 43.2 minutes of “budget” in 30 days during which the target can be missed. Once the budget is spent, non-essential releases are frozen.

How to use this for an agent application:

  1. Set 1–3 SLOs per agent scenario: for example “customer-support agent resolution-rate SLO = 85%”, “p99 end-to-end latency SLO ≤ 5s”, “average cost per task SLO ≤ $0.05”
  2. Alert: warn when the live SLI drops below 80% of the SLO, and page oncall when it drops below the SLO
  3. Freeze releases: once the error budget is burned, do not merge anything that is not an emergency fix
  4. Business SLO vs technical SLO: business SLOs (conversion rate / CSAT / GMV) are product acceptance; technical SLOs (latency / error rate / cost) are the engineering backstop. Both layers are required

Rule of thumb: a stricter SLO is not automatically better — 99.99% costs 5–10× more than 99.9%, and it is likely past the threshold users can perceive. Google recommends the level that is just high enough that users don’t complain.

TTL / Time To Live Software engineering — how long data, a cache entry, or a credential stays valid

It expires automatically. Common uses:

  • Cache TTL: a Redis cache set to 1h / 24h
  • Prompt Caching TTL: Anthropic defaults to 5 minutes, with an optional 1 hour
  • Session TTL: a user session of 24h–7d
  • Credential TTL: JWTs and temporary AWS credentials are usually 1h
  • Memory TTL: a short TTL for low-confidence memories and a long TTL for high-confidence ones (one defense against memory corruption)

LLM fundamentals

token LLM basics — the smallest input/output unit of an LLM, produced by a tokenizer
  • English: one token usually corresponds to one common word or half of a long word (about 4 characters)
  • Chinese: one token corresponds to about 0.5–2 characters (depending on how the tokenizer was trained)
  • Code: punctuation, indentation, and symbols each take tokens

A rule-of-thumb conversion: 1000 English words ≈ 1300 tokens; 1000 Chinese characters ≈ 1500–2000 tokens.

Why it matters: the context window, API billing, and inference speed are all counted in tokens. Controlling the token count = controlling cost and latency. Anthropic, OpenAI, and Google each have their own tokenizer, and a ±20% difference in token count for the same text is common.

embedding LLM basics — map text or an image to a high-dimensional dense vector; semantically similar vectors sit close together

Text → a neural network → a vector of 768 / 1024 / 1536 / 3072 floating-point numbers. Vectors for synonyms or same-topic text sit close together in that space (high cosine similarity).

Main uses:

  • Retrieval: a query embedding → find the most similar document embeddings (RAG recall)
  • Clustering: automatically group documents on similar topics
  • Classification: zero-shot classification by similarity
  • Dedup: similarity above a threshold counts as a duplicate

Mainstream models in 2026: OpenAI text-embedding-3-large, Cohere v4, Voyage-3, BGE-M3 (open-source SOTA; Chinese–English bilingual, combining dense / sparse / multi-vector).

context window / context window LLM basics — the token limit a model can process in one call

It includes the system prompt, conversation history, user input, and model output; all of them count. Mainstream models in 2026:

  • GPT-4o: 128k
  • Claude 3.5 Sonnet / Opus: 200k
  • Gemini 1.5 Pro: 1M–2M
  • Llama 3.1: 128k

Note: the advertised window ≠ the effective window. The RULER benchmark shows that most models’ performance drops sharply beyond 1/4 of the window (Lost in the Middle). Engineering guidance sets the threshold for “what should go into context” at 8–32k; anything longer goes through RAG or hierarchical summarization.

prefill / decode LLM basics — the two phases of LLM inference: process the input, then generate token by token
  • Prefill: feed every prompt token into the model at once and compute the KV cache. Compute-bound (limited by GPU compute); the whole prompt can be processed in parallel in one shot. Its latency determines TTFT.
  • Decode: generate one token at a time, and each token reuses the KV cache of every preceding token. Memory-bound (limited by memory bandwidth). Its latency determines TPOT / ITL (inter-token latency).

The two phases have different bottlenecks, so the tuning strategies differ too — prefill is optimized with parallelism / FlashAttention, and decode is optimized with continuous batching / speculative decoding. Because the two phases have opposite characteristics, engineering also uses two kinds of scheduling optimization: PD disaggregation (Prefill/Decode Disaggregation, handling the phases on different GPU pools, as in DistServe/Mooncake) and chunked prefill (split a long prefill into chunks and interleave them with decode). See A11 for detail.

KV cache LLM basics — a cache of the K (Key) and V (Value) matrices already computed for attention

Generating token t needs the K/V of every earlier token in the attention computation. Caching them so they are not recomputed every time is the most basic optimization in LLM inference.

Memory use: 2 × num_layers × num_heads × head_dim × seq_len × batch × bytes_per_elem. On a 70B model, the KV cache for a 128k context can reach tens of GB, far more than the model weights themselves.

Further optimizations:

  • PagedAttention: manage it in blocks and remove fragmentation
  • GQA/MQA: fewer K/V heads, shrinking the KV cache to 1/8 ~ 1/H
  • KV-cache quantization: an FP8 KV cache (native on H100) cuts memory in half
  • prefix caching: reuse the KV of an identical prefix across requests
autoregressive / autoregressive LLM basics — generate one token at a time; the next token depends on every token before it

How GPT-style decoder-only models generate: P(x_t | x_1, ..., x_{t-1}). Every generated token runs a full forward pass (even though the KV cache can be reused), so output length directly determines latency.

By comparison: BERT is non-autoregressive (masked LM: it predicts every masked position at once), and diffusion models are also non-autoregressive (they denoise the whole span in one shot).

The cost of autoregression produced a large family of speedups: speculative decoding, parallel decoding, Medusa, EAGLE, and others.

logit LLM basics — the model’s raw unnormalized scores, one value per vocabulary token

The last decoder layer outputs a logit vector of dimension [vocab_size]; after softmax it is the probability distribution of the next token.

Places engineering can get the logits (or top-k logprobs):

  • Computing perplexity (how “surprised” the model is by the text)
  • Self-Consistency weighting candidates by logprob
  • An LLM-as-judge using the yes/no logit difference as confidence
  • The DPO loss computed directly from logprobs
  • Speculative decoding using logits for rejection sampling

Note: commercial OpenAI / Anthropic APIs return only the sampled result by default; you have to turn the logprobs option on explicitly.

temperature LLM basics — a hyperparameter that controls sampling randomness; 0 = deterministic, >1 = highly random

P(token) ∝ exp(logit / T):

  • T=0: greedy, always pick the argmax, reproducible (same input, same output)
  • T=0.7–1.0: the recommended range for general chat
  • T>1: higher means more random; diversity goes up, but so does nonsense

Turn it up when: Self-Consistency needs diverse paths, creative writing, brainstorming. Turn it down when: code generation, math reasoning, strict formatted output, T=0.1–0.3.

Trap: T=0 is not fully identical to deterministic — non-determinism of floating-point GPU kernels plus concurrent scheduling can still leave tiny differences for the same prompt.

attention sink LLM basics — the phenomenon where the model concentrates a large share of attention on the first few tokens of the sequence

Xiao et al. 2023 found that during long-sequence inference, later tokens often assign a disproportionate share of attention to the first few tokens of the sequence (even when those tokens are semantically unrelated). Those tokens become a “sink” and absorb the normalization mass that softmax is required to distribute.

Why it matters in engineering:

  • StreamingLLM: sliding-window inference that keeps the leading sink tokens, so it can handle sequences of unbounded length
  • It explains Lost in the Middle: attention on middle tokens is squeezed by the head and the tail
  • It explains why truncating the start of the sequence hurts performance sharply — the sink is gone

Transformer architecture

LayerNorm / RMSNorm Architecture — the mainstream normalization layers in Transformers; normalize a single sample along the feature dimension

LayerNorm: y = (x - μ) / σ * g + b, mean and variance taken along the hidden dimension. Independent of the batch, so it naturally supports variable-length sequences and single-example inference — which is why Transformers use LayerNorm rather than BatchNorm.

RMSNorm (Zhang & Sennrich 2019): y = x / sqrt(mean(x²)+ε) * g, dropping the mean subtraction and the bias. Modern LLMs such as Llama, PaLM, and Mistral have almost all switched to RMSNorm, saving 7–64% of normalization time without hurting quality.

Pre-LN vs Post-LN: doing LN before the residual (Pre-LN) trains more stably than doing it after the residual (Post-LN), and warmup can be dropped. From GPT-2 onward, Pre-LN is nearly universal.

RoPE / Rotary Position Embedding Architecture — rotary position embeddings; encode position into a rotation matrix applied to Q/K

Su et al. 2021. Represent position m as a rotation matrix R_m applied to Q/K, so that <R_m·q, R_n·k> = f(q, k, m-n) — the attention score depends only on relative distance.

Advantages: (1) no extra parameters; (2) relative position is encoded naturally; (3) compatible with linear attention. It has become the position-encoding scheme of the great majority of modern LLMs, including Llama, Qwen, and Mistral.

The extrapolation problem: naive extrapolation from 2k to 32k collapses — the rotation angles of high-frequency components fall into regions never seen in training. Mitigations:

  • NTK-aware scaling: interpolate low-frequency dimensions and leave high frequencies approximately unchanged
  • YaRN (Peng 2023): add an attention temperature and scale by dimension bands. Llama-3.1 128k and Qwen2.5 use this scheme
NTK-aware scaling / YaRN Architecture — RoPE length-extrapolation schemes that let a model trained at 2k run a 32k / 128k context

Naive extrapolation of RoPE collapses — the rotation angles of high-frequency components fall into regions never seen outside the training context. Two engineering schemes:

  • NTK-aware scaling (NTK = Neural Tangent Kernel): interpolate the low-frequency dimensions (stretch the base) and leave the high-frequency dimensions nearly unchanged. Simple and effective; no retraining required.
  • YaRN (Peng et al. 2023): on top of NTK, add an attention temperature adjustment and piecewise scaling by frequency dimension (high frequencies kept strictly, low frequencies interpolated hard). It needs a small amount of long-context fine-tuning (samples on the order of tens of thousands of tokens).

Where they are used:

  • Llama-3.1 128k → YaRN
  • Qwen2.5 / Qwen3 → YaRN
  • Early Mistral-7B 32k → NTK
  • GPT-4 / Claude → closed source; they may use an in-house scheme plus continued long-context training

Numbers from practice: YaRN is nearly lossless at a 4× context extension (2k→8k or 32k→128k); beyond 8× there is still a performance drop. Extreme long context (1M+) usually needs retraining rather than YaRN alone.

GQA / MQA Architecture — Grouped/Multi Query Attention; several Q heads share one set of K/V heads

Standard multi-head attention: each of the H heads has its own Q/K/V.

  • MQA: every Q head shares one set of K/V (the extreme form)
  • GQA: split the H Q heads into G groups, and each group shares one set of K/V (a compromise). G=H/8 is a common setting

The gain: the KV cache shrinks to 1/8 ~ 1/H, inference throughput rises substantially, and quality is almost unchanged. Llama-2 70B, Llama-3, Mistral, Qwen2, and others use GQA.

MoE / Mixture of Experts Architecture — a mixture-of-experts model; each token activates only some of the expert FFNs

Replace the traditional dense FFN with N parallel expert FFNs plus a router. Each token picks the top-k experts through the router (k is usually 1–2) and only those experts are activated for the compute.

Advantage: a large parameter count with little compute. Mixtral 8x7B has 47B total parameters and only 13B activated; DeepSeek-V3 has 671B total parameters and only 37B activated. At the same inference cost, capacity far exceeds a dense model.

Challenges: (1) load balancing during training (so one or two experts are not overused); (2) memory is counted by total parameters, not activated parameters; (3) communication cost is high (expert parallelism).

multi-head attention / multi-head attention Architecture — split d_model into h independent Q/K/V projections; each head learns relations in a different subspace

Single-head attention produces one attention distribution for each pair of tokens — one “relational viewpoint”. Multiple heads (h=8/32/64/128) let the model learn several relations at once: syntactic heads attend to short-range dependencies, and semantic heads attend to coreference and long-range entities.

Why a single head with a larger dimension does not work: multi-head is a mixture of h low-rank attentions and is strictly more expressive; a single head is one high-rank attention and has fewer degrees of freedom.

A further variant: GQA / MQA drops heads on the KV side to save memory, while the Q side stays multi-head.

Inference acceleration

FlashAttention Inference acceleration — attention computed with tiling + online softmax, without materializing the full attention matrix

Dao 2022. Standard attention uses O(N²) memory (it stores an N×N attention matrix), which bottlenecks long sequences. FlashAttention loads Q/K/V in blocks into GPU SRAM for the compute and does not write out the full attention matrix. Memory drops to O(N), and it is also faster — attention is memory-bound, so reading less HBM makes it faster.

The line of work:

  • FA1 (2022): ~25% of peak FLOPS on A100
  • FA2 (2023): better parallel partitioning and warp scheduling, ~50–72% of peak on A100
  • FA3 (Shah 2024): targets the H100 with WGMMA asynchronous tensor cores + TMA + producer/consumer warps. BF16 reaches 740 TFLOPS (75% of peak), and FP8 approaches 1.2 PFLOPS
PagedAttention Inference acceleration — proposed by vLLM; manage the KV cache as fixed-size blocks, the way an OS manages virtual memory

Kwon et al. 2023. It addresses three kinds of fragmentation in the traditional inference KV cache:

  • Internal fragmentation: max_seq_len is preallocated, but only a small part is actually used
  • External fragmentation: gaps between requests cannot be reused
  • Shared prefixes cannot be deduplicated

Mechanism: cut the KV cache into fixed-size blocks (for example 16 tokens), and each sequence keeps a block table (a logical→physical mapping). Memory utilization rises from ~20% to >96%; multiple samples of the same prompt share prefix blocks; together with continuous batching, throughput is 2–4× HuggingFace TGI and 24× FasterTransformer.

vLLM Inference acceleration — UC Berkeley’s open-source high-throughput LLM inference engine, which implements PagedAttention

The de facto standard open-source inference server since 2023. Core features:

  • PagedAttention memory management
  • Continuous batching
  • Prefix caching, on by default
  • Chunked prefill (the default in v0.6+, interleaving prefill and decode to cut jitter)
  • FP8 KV cache (H100/H200)
  • Support for GPTQ / AWQ quantization

Compared with: TGI (HuggingFace), TensorRT-LLM (NVIDIA; proprietary and faster), SGLang (more thorough prefix reuse), LMDeploy (from OpenCompass).

continuous batching Inference acceleration — dynamic scheduling at token granularity; a request leaves as soon as it finishes, and a new request can join at any time

Also called in-flight batching, proposed by Yu et al., ORCA, 2022. Compared with static batching (wait until the batch is full and then run together; when short and long requests are mixed, GPU utilization is often <30%), continuous batching:

  • After each decode step, finished requests leave immediately
  • A newly arrived request immediately takes a free slot, runs prefill first, then joins the decode batch
  • Together with PagedAttention, there is no memory fragmentation

vLLM’s numbers: throughput is 5–23× static batching. It is now the default in every modern inference engine.

speculative decoding Inference acceleration — a small draft model quickly guesses K tokens, and the large model verifies them in parallel with one forward pass

Leviathan et al. 2023. The procedure:

  1. A small draft model (1–7B) autoregressively generates K tokens (K=5 is typical)
  2. The large target model (70B+) verifies K+1 positions in parallel with one forward pass
  3. The first j are accepted and the (j+1)th is rejected → keep the first j and sample one new token

Mathematically this guarantees the output distribution matches the original model exactly (rejection sampling).

When it pays off: (1) the draft and target distributions are similar (acceptance rate >60%); (2) the large model is memory-bandwidth bound, so parallel verification does not add latency. Acceptance rate is 70–90% for code generation and 30–50% for open-ended generation. Variants: EAGLE-2/3, Medusa, Llama 3.1 self-speculative.

prefix caching Inference acceleration — cache the KV cache of a shared prefix across requests and skip recomputing the prefill

The KV cache is reuse within a single request; prefix caching is reuse across requests. When many requests share a system prompt / few-shot examples / agent history, compute that KV once, cache it, and later requests hit the cache and skip prefill.

Effect: in agent / RAG / multi-turn settings, the system prompt is usually 1–4k tokens and shared by almost every request, so TTFT can drop 10–100×.

Implementations: vLLM --enable-prefix-caching, SGLang RadixAttention (a radix tree that automatically manages every historical prefix), the Anthropic prompt caching API (5-minute TTL; the cached portion is priced at 0.1×).

TTFT / Time to First Token Inference acceleration — latency from sending the request to the first token coming back

Driven mainly by prefill (processing every input token). One of the core metrics for billing and monitoring.

Ways to lower TTFT:

  • Prefix caching (after a hit, TTFT drops 80%+)
  • Shorten the prompt (once RAG recall is accurate enough, chunks can be cut)
  • FlashAttention / newer hardware
  • Speculative decoding
  • Chunked prefill (does not block other requests’ decode)

Companion metric: TPOT (time per output token, the gap between tokens, also called TBT/ITL) — determined by decode.

TPOT / Time Per Output Token Inference acceleration — average latency per generated token in the decode phase (also called ITL / TBT)

The other core latency metric, paired with TTFT: TTFT measures “how long until the first character appears” (determined by prefill), and TPOT measures “how fast each following character appears” (determined by decode). Perceived speed of streaming ≈ 1/TPOT (tokens/s).

  • Aliases: ITL (inter-token latency), TBT (time between tokens).
  • Bottleneck: decode is memory-bound; TPOT is driven mainly by memory bandwidth and batch size.
  • Ways to lower it: continuous batching raises throughput, speculative decoding emits several tokens per step, and GQA/MQA / KV quantization shrink how much KV cache is read.
  • SLA practice: TTFT and TPOT are often given separate targets (for example p99 TTFT < 1s, TPOT < 50ms) and optimized independently via PD disaggregation / chunked prefill.

Quantization

FP16 / BF16 / FP8 Quantization — low-precision floating-point formats that save memory and compute
  • FP16 (half): 5-bit exponent + 10-bit mantissa, narrow dynamic range, training overflows easily
  • BF16 (brain float): 8-bit exponent + 7-bit mantissa, the same dynamic range as FP32, lower precision but stable training; the default training precision from A100/H100 onward
  • FP8 (native on H100/H200): E4M3 (forward) + E5M2 (backward), a dynamic range ~10⁴× larger than INT8, almost no accuracy loss, and throughput is 2× BF16

Mixed-precision training: weights and gradients in BF16/FP16, optimizer state still in FP32.

INT4 / INT8 / NF4 Quantization — integer quantization that compresses FP16 weights to 4/8-bit integers

At deployment, quantize weights to low-bit integers and dequantize back to floating point for inference.

  • INT8: accuracy loss is usually <1%, and deployment is straightforward
  • INT4 (GPTQ / AWQ): a 7B model shrinks from 14GB to ~4GB, so a consumer GPU can run a large model
  • NF4 (NormalFloat 4-bit, used by QLoRA): information-theoretically optimal quantization for a normal distribution, designed for LLM weight distributions

INT8 / INT4 quantization usually needs a calibration set (128–512 samples); AWQ is smarter (it protects the 1% salient channels). For extreme memory budgets, use GGUF (the llama.cpp format) plus 3-bit / 2-bit quantization to run on phones.

AWQ / Activation-aware Weight Quantization Quantization — INT4 weight quantization that protects the 1% salient channels

Lin et al. 2023. The core observation: protecting only ~1% of the “important weight channels” (identified by activation magnitude) is enough to hold accuracy. Scale those channels up per channel, then quantize.

Compared with GPTQ: simpler to implement, lower perplexity on Llama-2, and now the default in vLLM / TensorRT-LLM.

GPTQ Quantization — an earlier post-training 4-bit weight quantization method

Frantar 2022. Layer-wise minimization of quantization error, inspired by OBQ, with a small calibration set (128 samples). Pros: early, and the ecosystem is complete (exllama / vllm / TGI all support it). Cons: sensitive to the activation distribution; important channels can be crushed.

Deployment choices in 2026: H100/H200 → FP8; A100/3090 → AWQ INT4; phones/edge → INT4 + GGUF.

Fine-tuning and alignment

SFT / Supervised Fine-Tuning Fine-tuning — supervised fine-tuning: train the model on (prompt, response) pairs

The most basic form of instruction tuning: treat (input, desired output) pairs as supervised samples and use cross-entropy loss to teach instruction following.

Data volumes from practice:

  • Format/style adaptation on a chat model: 500–5000 high-quality samples
  • Inject new domain knowledge: 10k–100k samples mixed with 5–20% general data
  • Full instruct tuning from a base model: millions of samples (Llama 3 uses ~10 million)

The LIMA paper: 1000 curated samples can bring a 65B base close to GPT-4 conversation quality — quality >> quantity.

LoRA / Low-Rank Adaptation Fine-tuning — freeze the original weights and train only low-rank adapter matrices

Hu et al. 2021. Factor the weight update into two low-rank matrices ΔW = BA (r=8/16/64) and train only those matrices, cutting trainable parameters by 100–10000×.

Memory:

  • Full fine-tuning ≈ 16–20× the parameter bytes; a 7B model needs >100GB
  • LoRA: the frozen original weights still load in FP16, so a 7B model needs ~14GB plus the adapter

Advantages: few trainable parameters / multiple adapters can be hot-swapped / mitigates catastrophic forgetting.

QLoRA Fine-tuning — 4-bit quantized frozen weights plus a LoRA adapter; fine-tune a 65B model on a single 24GB GPU

Dettmers et al. 2023. Three key pieces:

  1. 4-bit NF4 quantization of the frozen weights: a 7B model shrinks from 14GB to ~4GB
  2. Double Quantization: quantize the quantization constants too, saving ~0.4 bit/param
  3. Paged Optimizer: NVIDIA unified memory; on OOM, spill to CPU

QLoRA for a 65B model is about 33GB and fits on one A100-48G or two RTX 3090s. Cost: training is 30–40% slower (dequantization overhead).

RLHF Alignment — Reinforcement Learning from Human Feedback: RL training from human preferences

Three steps: (1) SFT trains a base policy; (2) humans label (chosen, rejected) preference pairs to train a Reward Model; (3) the RM scores policy outputs, and algorithms such as PPO/RLOO/REINFORCE update the policy.

InstructGPT and ChatGPT brought RLHF into the mainstream. Three major pain points:

  • Training the RM needs a large amount of human preference labels (on the order of 100k pairs), which is expensive
  • The RM is easy to hack (the policy learns to flatter the RM’s surface preferences)
  • Preferences on subjective tasks are noisy to begin with

This produced simplifications and improvements such as DPO, GRPO, and RLVR.

RM / Reward Model Alignment — a “scoring model” trained on human preferences that scores LLM outputs

Trained in step two of RLHF. Input: (prompt, response). Output: a scalar reward. The training loss is Bradley-Terry: make the RM score chosen higher than rejected on (chosen, rejected) pairs.

Common weaknesses:

  • Reward hacking: the policy learns to flatter the RM’s surface preferences (length, a particular opening)
  • Goodhart’s Law: once the RM becomes the RL objective, it no longer represents true human preference
  • Poor generalization: RM scores are not trustworthy outside the training distribution

Alternatives: DPO removes the RM entirely, and RLVR uses a programmatically judged reward.

DPO / Direct Preference Optimization Alignment — a mathematical proof that you can skip the RM and optimize preferences with a supervised loss

Rafailov et al. 2023. It proves that under a Bradley-Terry preference model plus a KL constraint, the optimal policy has a closed form, so preference pairs (chosen, rejected) can be used directly as a supervised loss:

L_DPO = -log σ(β(log π(y_w)/π_ref(y_w) - log π(y_l)/π_ref(y_l)))

Advantages: (1) no RM / no online sampling / no critic; only the policy and a reference model; (2) uses the same training stack as SFT; (3) hyperparameters are stable.

Disadvantages: depends heavily on preference-data quality; easy to overfit surface patterns of the chosen answers; high reward-hacking risk.

The main post-training path for Llama-3 and Qwen2 is DPO or a variant (IPO, KTO, SimPO).

PPO / Proximal Policy Optimization Alignment — the classic RLHF algorithm: actor-critic plus a clipped objective

Schulman 2017. The actor learns the policy, the critic learns a value function to estimate advantage, and clipping limits how far the policy can move each step so it doesn’t collapse.

RLHF must load four models at once — actor / ref / critic / reward — so memory is ≥4× a single model. Hyperparameters are sensitive (KL coefficient, clip ratio, advantage normalization), and training is unstable.

This produced simplifications such as DPO (drop RL), GRPO (drop the critic), and RLOO (use mean reward as the baseline).

GRPO / Group Relative Policy Optimization Alignment — proposed by DeepSeek; drops the critic and uses the within-group mean reward as the baseline

Proposed in DeepSeek-Math 2024 and validated by R1. The core change: drop the critic (the value network). Sample G responses for the same prompt (typically G=64), normalize advantage by the within-group mean and standard deviation of the reward: A_i = (r_i - mean(r)) / std(r), then apply a PPO-like clipped objective plus KL regularization.

Effects:

  • Memory is cut in half (no critic), so RL at the 70B scale is feasible with reasonable resources
  • Within-group normalization supplies a baseline for free, and variance is even lower than PPO’s GAE
  • Together with RLVR, R1-Zero emerges long CoT from a base model by pure RL
RLVR / RL with Verifiable Rewards Alignment — RL with a programmatically judged 0/1 reward; no RM required

On tasks that can be checked automatically — math, code, formal logic — use a program as the reward: answer match, unit tests passing, a theorem prover verifying.

Advantages:

  • No labeling cost
  • The signal is clean, with no room for RM hacking
  • Rollouts can be parallelized at large scale

DeepSeek-R1 and DAPO (ByteDance’s open-source SOTA) are both in this family. Limitation: it applies only to verifiable tasks; open-ended dialogue still needs RLHF / DPO.

catastrophic forgetting / catastrophic forgetting Fine-tuning — after fine-tuning on a new task, general capability drops sharply

Mechanism: parameters are pulled by the new task’s loss, and directions that encoded general knowledge get overwritten.

A mitigation mix (recommended in production):

  • Mix 5–30% general data into the new data
  • LoRA rather than full parameters (a low-rank constraint)
  • A small learning rate (starting at lr=1e-5) plus short training (1–2 epochs)
  • Keep evaluating MMLU / MT-Bench as a monitor

Advanced: EWC (Fisher-information-weighted L2 regularization), model souping (average the fine-tuned weights with the original model), and extending MoE routing.

Prompting and reasoning patterns

CoT / Chain of Thought Prompting — have the model write reasoning steps before the answer

Wei et al. 2022. The simplest form: “Let’s think step by step” (Kojima 2022 zero-shot CoT).

Why it works: (1) more effective compute (more forward steps); (2) it turns “System 1” intuitive answers into “System 2” step-by-step reasoning; (3) it exposes faulty reasoning so self-consistency voting can correct it.

It is an emergent ability and is almost useless on models under 10B. Long CoT (trained with RL in R1 / o1, including backtracking and self-verification, thousands of tokens long) is the new paradigm of 2025.

ToT / Tree of Thoughts Prompting — model reasoning as tree search: several candidates per step, plus self-evaluation and backtracking

Yao et al. 2023. CoT is a single linear chain and cannot go back once it is wrong. ToT generates several candidate thoughts at each step, the LLM self-evaluates state value (promising / sure / impossible), and BFS/DFS expansion can backtrack and prune.

On Game of 24, GPT-4 CoT scores 4% vs ToT 74%. Cost: LLM calls rise from 1 to 50–200.

Fits: solution spaces that need explicit search (puzzles, planning, theorem proving) where intermediate states can be scored. Does not fit: chitchat, summarization, translation.

ReAct Prompting — Reasoning + Acting: a think–act–observe loop

Yao et al. 2022. The structure is a Thought → Action → Observation loop: the model first writes “Thought: I need to look up X”, then outputs “Action: search[X]”, the tool result is fed back into the prompt as “Observation: …”, and the next Thought follows.

Three effects:

  • Hand facts the model does not know off to tools, which reduces hallucination
  • Reasoning is steered by observations, so a mistake can be corrected
  • It leaves an interpretable trace that is easy to debug

It is the conceptual prototype of modern agent frameworks (Claude tool use, OpenAI function calling, LangChain, AutoGPT).

Reflexion Prompting — “verbal reinforcement learning” across episodes: store the reason for failure as a lesson

Shinn et al. 2023. After a task fails (an external verifier gives a binary reward), the agent uses an LLM to summarize the cause as a natural-language lesson, stores it in episodic memory, and adds that lesson to the prompt on the next task to change behavior.

vs Self-Refine:

  • Self-Refine optimizes within a single episode and relies only on the model’s self-critique
  • Reflexion learns across episodes and has an external ground-truth verifier

On HumanEval, GPT-4 with Reflexion scores 91%, above the GPT-4 baseline of 80%.

Self-Refine Prompting — iteration inside a single task: a generate → self-feedback → refine loop

Madaan et al. 2023. Loop N rounds inside one trajectory, with no external reward and no cross-task memory. Average gain of 20% across 7 tasks.

Trap: a weak model’s self-critique is inaccurate and revisions can get worse. Production often combines Self-Refine (within an episode) with Reflexion (across episodes).

self-consistency Prompting — sample N CoT traces for the same question and majority-vote the final answer

Wang et al. 2022. With temperature>0, sample N CoT paths and vote on the final answer. On GSM8K this is about 17 percentage points above greedy CoT (PaLM 55%→74%).

Pays off when: (1) the answer space is discrete (numbers, multiple choice); (2) the model’s error rate is <50%; (3) reasoning paths are diverse (temperature 0.7–1.0). Cost: N× (typically N=5–40). It does not apply to open-ended generation.

few-shot / zero-shot Prompting — whether the prompt includes examples
  • Zero-shot: state the request directly, with no examples. “Translate into English: 你好”
  • Few-shot (in-context learning): put 1–N (input, output) examples in the prompt. The GPT-3 paper systematized this first.

When to use few-shot: (1) the task format is novel or the output structure is complex (a JSON schema, a specific markdown layout); (2) a classification task has many labels.

When to use zero-shot: modern models are already saturated on general tasks (summarization, translation, QA), and adding examples can introduce bias.

Traps: example order matters a lot (recency bias); accidental regularities get learned; too many examples run into Lost in the Middle. Keep it to ≤8.

RAG

RAG / Retrieval-Augmented Generation RAG — retrieval-augmented generation: retrieve relevant documents first, then have the LLM answer from that context

The standard pipeline = Ingestion + Retrieval + Generation:

  1. Ingestion: document loader → chunking → embedding → write to the vector store
  2. Retrieval: query rewriting → embedding → vector search → reranker → top-k
  3. Generation: build the prompt (including retrieved chunks) → LLM generation → post-processing + citation

Every stage has a bottleneck: chunk size, embedding choice, insufficient recall, context order, and the model not staying faithful to the context. Production RAG ≠ “embedding + a vector store + an LLM” — it is an engineering system.

chunking RAG — split a document into small pieces suitable for embedding / retrieval

Strategies:

  • Fixed: by token count plus overlap. Simple, but it easily cuts in the middle of a sentence
  • Recursive / Structural: split on markdown headers / code blocks / paragraphs. The production default
  • Semantic: split by embedding similarity between sentences
  • Late Chunking (Jina 2024): run a long-context embedding over the whole document first, then cut at token level
  • Contextual Retrieval (Anthropic 2024): prepend an LLM-generated “context prefix” to each chunk before embedding; the retrieval failure rate drops 49%
BM25 RAG — the classic sparse retrieval algorithm based on term frequency plus IDF

Okapi BM25. Relevance of a document to a query is Σ IDF(qi) · f(qi,d) · (k+1) / (f + k·(1-b+b·|d|/avgdl)). Strengths: exact term hits, high weight on rare terms, proper nouns, numbers. Weakness: synonyms don’t match (“医生” vs “doctor”).

It complements dense embeddings — hybrid search fuses the two, and recall is 5–15 percentage points above dense alone.

hybrid search RAG — dual-path recall from dense embeddings plus BM25, then fusion

Dense embeddings are good at semantic similarity; BM25 is good at exact term match; the two complement each other.

Fusion methods:

  • RRF (Reciprocal Rank Fusion): score(d) = Σ 1/(k + rank_i(d)), k=60. The production default; the two score streams do not need to be normalized
  • Weighted sum: α·dense + (1-α)·bm25. You have to tune α and normalize the scores
  • Learned fusion: feed the top-N to a reranker, which takes over the final ranking

Anthropic’s Contextual Retrieval experiment: embedding alone → + contextual embedding → + BM25 → + rerank, with failure rates 5.7% → 4.0% → 3.7% → 1.9%.

reranker / cross-encoder RAG — rescore the recalled top-N with a more accurate (and slower) model

Bi-encoder (embedding): encode the query and the doc separately, then compare by cosine. Fast, but there is no interaction. Cross-encoder (reranker): concatenate query + doc and feed them to a transformer; self-attention at every layer lets them interact. Relevance modeling is 20–40% stronger (NDCG@10), and it is 100× slower.

The production standard: bi-encoder recalls top-100 → cross-encoder reranks to top-10 → feed the LLM.

Mainstream: Cohere Rerank v3/v4, BGE-reranker-v2-m3 (open-source SOTA for Chinese and English), Jina Reranker v2, Mixedbread.

Trap: if the relevant document is not in the recalled top-100, reranking cannot save it — a reranker improves what was already recalled and cannot stand in for recall.

Choosing a mainstream embedding model RAG — how to choose among BGE-M3 / Cohere v4 / Voyage-3 / OpenAI text-3-large / Qwen3-Embedding

A 2026 comparison of mainstream embedding models:

  • OpenAI text-embedding-3-large (3072-d): the English baseline, API-friendly, $0.13/M tokens; Chinese is only average.
  • Cohere embed-v4 (1024–1536-d, multimodal): top tier on MTEB v2, text and images in the same space, 100+ languages; the default choice for enterprise SaaS.
  • Voyage-3-large (1024-d): first overall on MTEB v2, strong in Chinese, slightly ahead of Cohere on retrieval.
  • BGE-M3 (BAAI, 1024-d): open-source SOTA, supports dense + sparse + multi-vector (ColBERT-style) at once, Chinese–English bilingual; the default for self-hosting.
  • Qwen3-Embedding-8B (Alibaba, 2025): one of the open-source Chinese SOTAs; it and BGE-M3 each win on different tasks.
  • Conan-Embedding (Tencent) / Yi-Embedding (01.AI): Chinese-language options from domestic vendors.

Selection framework:

  1. Mostly Chinese → BGE-M3 / Voyage-3 / Qwen3-Embedding
  2. Multimodal → Cohere v4
  3. English-only + API → OpenAI text-3-large
  4. Self-hosted private deployment → BGE-M3

Key traps:

  • MTEB has version differences (v1 / v2 / MMTEB), and models cite different versions, so a head-to-head comparison misleads — re-benchmark on your own scenario
  • Dense vs sparse depends on the scenario: for exact term hits (proper nouns / IDs), mixing BM25 + dense (hybrid search) gains 5–15pp over dense alone
vector DB / vector database RAG — stores embeddings and supports approximate nearest-neighbor (ANN) search; Pinecone / Milvus / Qdrant and others

Mainstream:

  • Pinecone: SaaS, the enterprise default
  • Milvus: open source plus cloud
  • Qdrant: written in Rust, strong performance
  • Weaviate: includes knowledge-graph features
  • pgvector: a Postgres extension; if you already have Postgres, use it directly
  • Vespa / Elasticsearch: search engines extended with vectors
  • Chroma: friendly for local development

ANN algorithms: HNSW (the most common), IVF, ScaNN (Google). Index time vs retrieval accuracy vs memory is a trade-off.

GraphRAG / Self-RAG / CRAG / Agentic RAG RAG — four advanced variants of naive RAG, each addressing a different weakness

Naive RAG struggles with cross-document, cross-entity reasoning, unstable recall quality, and multi-hop queries. Four common advanced schemes:

  1. GraphRAG (Microsoft 2024): use an LLM to extract entities and relations from documents, build a knowledge graph, and write hierarchical summaries by community. At query time you can both vector-search and walk the graph. It addresses incomplete recall when naive RAG reasons across many documents and entities. Cost: ingestion gets much more expensive (one LLM extraction per chunk).
  2. Self-RAG (Asai 2023): train a single LM to emit reflection tokens that decide (a) whether to retrieve, (b) whether the retrieved text is relevant, (c) whether the answer is supported by the context, and (d) overall utility. It addresses the judgment of when to retrieve and how to use what was retrieved. Requires training.
  3. CRAG (Corrective RAG, Yan 2024): a lightweight evaluator scores retrieved chunks. High scores are used directly, middling scores trigger a fresh web search, and low scores fall back to ungrounded generation. It addresses blindly using retrieved text when recall quality is uneven.
  4. Agentic RAG: the agent decides query rewriting → multi-round retrieval → division of work among sub-agents. It addresses multi-hop questions that need iterative retrieval. DeepResearch-style products are on this path.

Practical choice:

  • Ordinary QA → naive RAG + a reranker
  • Complex cross-document, cross-entity reasoning → GraphRAG
  • Unstable recall quality → CRAG
  • Multi-hop reasoning / iterative search → Agentic RAG
RAGAS RAG — the de facto standard for RAG evaluation; all four core metrics are implemented with an LLM-as-judge

Es et al. 2023. The four metrics:

  1. Faithfulness: whether each claim in the answer follows from the retrieved context. <0.7 = the model is making things up
  2. Context Precision: the share of the top-K that is truly relevant. Low = the retriever recalled noise
  3. Context Recall: whether the ground-truth information was all retrieved. Low = incomplete recall
  4. Answer Relevancy: whether the answer actually addresses the original question

Production thresholds: all four ≥0.7 counts as passing; if Faithfulness < 0.7, fix that first; if Context Recall < 0.7, tune the retriever.

Agent engineering

harness / harness engineering Agent — the code skeleton and engineering system wrapped around an LLM, so the agent physically cannot repeat a mistake

Named by Mitchell Hashimoto in 2026: “anytime you find an agent makes a mistake, take the time to engineer a solution such that the agent never makes that mistake again.”

This is not model fine-tuning. It is an engineered environment that makes it physically impossible for the model to fail in the same way again.

Two laws:

  1. Strong constraints: if a deterministic constraint can do it (a hard failure from lint / type check / sandbox / CI), don’t use a prompt
  2. Self-healing loop: the agent can take ground truth from the environment, evaluate itself, and resume from a checkpoint after failure

OpenAI’s formula: Agent = Model + Harness; “Humans steer. Agents execute.”

LangChain / LangGraph / LlamaIndex / Haystack Agent — mainstream frameworks for building agents and LLM applications

A comparison of mainstream frameworks, 2024–2026:

  • LangChain (Harrison Chase / LangChain Inc.): the first LLM application framework to go mainstream. It positions itself as the “glue for LLM apps” — connecting LLMs, prompt templates, tools, vector stores, and document loaders. Strength: the fullest ecosystem. Weakness: many abstraction layers make over-wrapping easy, and Anthropic’s Building Effective Agents explicitly argues against “over-abstraction”.
  • LangGraph (LangChain Inc.): stateful graph orchestration built on LangChain — model an agent / workflow as nodes plus edges. Each node is an LLM call or a tool, and edges can branch on conditions. It fits complex multi-step / multi-agent coordination better than LangChain; it is one of the mainstream choices for multi-agent business systems such as Alibaba Fliggy.
  • LlamaIndex (Jerry Liu): focused on RAG, with a carefully designed document ingestion / indexing / retrieval / query pipeline. More specialized than LangChain when RAG is the heavy part of the system.
  • Haystack (deepset): an open-source RAG framework, enterprise-grade (including Kubernetes deployment / an API server), led by the European community.
  • Calling the Anthropic SDK directly: Anthropic recommends this in Building Effective Agents — for simple cases, calling the API directly is easier to understand and has fewer bugs than wrapping a framework around it.

Practice: prototype by calling the SDK directly; consider LangGraph once workflow patterns (routing / parallelization / orchestrator-workers) have settled; consider LlamaIndex for pure RAG; don’t start with the LangChain “full suite”.

MCP / Model Context Protocol Agent — an open protocol from Anthropic that lets an LLM client connect to external tools and data sources through one interface

Released in 2024-11, and moved to an independent Steering Committee in 2025-Q4 (Anthropic / Block / OpenAI / Microsoft). Three core primitives:

  • Resources: readable resources (files, DB rows)
  • Tools: callable functions (with a schema)
  • Prompts: reusable prompt templates

It solves the N×M problem of “writing a new adapter for every new tool”. The single fastest-growing skill in 2026, 97M+ monthly downloads, and already an explicit requirement on the Anthropic Applied AI Engineer JD.

tool use / function calling Agent — the LLM calls external functions through a structured schema

The model outputs {"name": "search", "arguments": {"query": "..."}} JSON; the runtime parses it, actually runs the function, and feeds the result back to the model. Anthropic’s Tool Use API and OpenAI function calling are the same idea.

Design principles (Anthropic’s measurements: “agent performance is proportional to how clear the tool descriptions are”):

  • Write tool descriptions like docstrings: purpose / parameters / return value / error cases
  • Small granularity, strong composition (Read / Edit / Bash / Grep rather than do_anything)
  • Forced preconditions (Edit requires Read-before-Edit)
  • Treat error messages as prompts (“command not found, did you mean X?”)
  • Deny-first permissions
Computer Use / Browser Agent Agent — let the model operate a desktop GUI or a browser

Anthropic released Computer Use in 2024-Q4. The loop: screenshot → the LLM looks at the image and reasons → it outputs mouse and keyboard actions (click X,Y / type text / scroll) → the system executes them → screenshot again.

Browser Use (an open-source framework) is similar but limited to the browser, based on Playwright plus DOM augmentation (overlay numbered labels on clickable elements in the screenshot).

Useful for: automating sites with no API, automating desktop software, end-to-end e2e tests. Limits: slow, expensive, weak on security, and poor support for canvas-rendered apps. Production advice: if an API exists, use the API.

sub-agent Agent — a subtask agent dispatched by the main agent, with its own context

The main agent hands “read 30 files and research them” to a sub-agent. The sub-agent has its own context window and returns only the final summary to the main agent — the main context is not polluted by intermediate artifacts.

Claude Code’s Task tool, OpenAI Swarm, CrewAI, and others support this. It is one of the key ways to prevent a Loop of Death and a context explosion.

AGENTS.md / CLAUDE.md Agent — a project manual written for the agent, stating protocols / constraints / the startup procedure

The agent reads it automatically when it enters the project. It usually contains:

  • Project background / architecture overview
  • A 5-step session startup protocol: pwd → git log → the progress file → start the dev server → run the basic tests
  • Coding standards / style constraints
  • Forbidden actions (production, sensitive directories, unsafe commands)
  • Known pitfalls / anti-patterns
  • How to run tests

Hashimoto’s view: each line of AGENTS.md ≈ one mistake sealed off. It is the implicit-prompt form of harness engineering.

deny-first Agent — deny every tool and command by default; only an explicit allowlist permits them

The permission model Claude Code uses. Bash commands are authorized at verb + path granularity:

  • git status allow
  • git push --force deny (destructive)
  • rm -rf pops a user confirmation
  • cat ~/.ssh/* deny (sensitive path)

The matching security principle: if any one layer fails, the others still catch it. Combine it with a sandbox, a network-egress allowlist, and a read-only filesystem for defense in depth.

progress file / progress.md Agent — persist agent task progress to a file so a later session can resume

A core design from Anthropic’s Effective Harnesses: a long-running agent will inevitably blow the context window, and LLM context alone cannot remember “which step I am on”.

The fix:

  • progress.md / PLAN.md: at each milestone the agent writes “finished X / currently on Y / next is Z / key decisions / risks”
  • git commit: every code change must be a git commit with a descriptive message. The git log is itself the work log, and you can roll back to any state

The next session runs the 5-step startup protocol and resumes from the breakpoint. Core insight: the context window is “working memory”; the filesystem is “long-term memory”.

Loop of Death Agent — the agent enters an infinite loop and burns tokens until they run out

Common patterns:

  • Retry loop: a tool fails → retry the identical call → fail again…
  • Goal drift: each step makes a small local fix, but the whole task doesn’t move
  • Mutual negation: multi-agent systems keep overturning each other’s decisions
  • Format hallucination: stuck hammering a tool-call format that never works

Defense in depth:

  1. A hard max iteration (5–30 steps)
  2. An execution timeout (5–30 minutes)
  3. A token budget (a per-task hard cap)
  4. Progress detection (force-stop after N consecutive steps with no diff)
  5. Repeated-failure detection (break out after the same tool call fails 3 times)
  6. Cost alerts + HITL
Memory Corruption / memory pollution Agent — a false fact enters long-term memory and then contaminates every later decision

Example: a user jokes “I’m a billionaire”, it is stored in semantic memory, and the agent reasons from that assumption from then on.

Defenses:

  • Write threshold: an LLM writes only when both “factual credibility” and “long-term value” are high
  • Provenance: every memory carries a source (user_said / tool_returned / inferred) plus confidence
  • TTL decay: low confidence gets a short TTL
  • Audit trail: every memory write has a trace_id
  • User-visible and user-editable: GDPR compliance plus a way to correct contamination
  • Prompt-injection defense: mark tool-returned data untrusted and do not write it directly

Evaluation and safety

Trace + eval tool stack Evaluation — observability platforms such as Langfuse / LangSmith / Phoenix / Helicone / Patronus

“Full-trace plus evaluation” tools for LLM apps and agents. Mainstream in 2026:

  • Langfuse (open source + SaaS): open-source SOTA, self-hostable, one place for traces + prompt versioning + eval + cost tracking. The default for small and mid-size teams.
  • LangSmith (LangChain Inc., closed-source SaaS): the deepest native integration with the LangChain ecosystem, good trace visualization, and a mature eval framework.
  • Phoenix (open source from Arize AI): focused on traces and monitoring for LLM apps, with a solid OpenTelemetry integration.
  • Helicone (open source + SaaS): a proxy mode that is fast to wire up, with clear monitoring of cost / cache hit / latency.
  • Patronus (SaaS): focused on a “hallucination / safety detector”, production-grade real-time blocking, aimed at enterprises.
  • Datadog / Grafana / Prometheus: general APM / metrics platforms are also starting to support LLM traces (Datadog LLM Observability, Grafana Tempo).

Capabilities to line up:

  1. Trace: prompt → tool_call → response → cost / latency strung into one complete trace
  2. Prompt versioning: each prompt change gets a hash, and the dashboard can switch and compare them
  3. Eval: run the gold set in CI and alert on regressions
  4. Cost and cache hit rate: cost per trace, and the distribution of cache hits
  5. User feedback / thumbs up-down: attach it directly to the trace and file bad cases

How to choose: prefer Langfuse if you self-host; LangSmith for heavy LangChain users; Phoenix for trace monitoring alone; Patronus for safety / real-time blocking.

Mainstream LLM eval benchmarks Evaluation — what MMLU / MT-Bench / Chatbot Arena / HumanEval / LiveBench / BFCL each measure

Grouped by the capability being measured:

  • MMLU (Massive Multitask Language Understanding): multiple choice across 57 subjects, a general-knowledge benchmark; GPT-4 ~88%. Criticism: severe item leakage, and multiple choice makes fine differences hard to see.
  • HumanEval (OpenAI 2021): 164 Python programming problems plus unit-test checks, a code-generation benchmark. It has been saturated (most frontier models are 90%+), it no longer separates models, and SWE-bench Verified is the recommendation.
  • MT-Bench (LMSYS 2023): 80 multi-turn dialogue questions, scored 1–10 by GPT-4 as judge. A classic benchmark of conversational ability, but judge bias is severe.
  • Chatbot Arena / LMArena (LMSYS / Berkeley): blind pairwise judgments by real people, scored by Elo. The most authoritative and the most expensive; since 2024 it has been suspected of score gaming (vendors specifically optimize Arena preferences such as “greetings / explanations / list formatting”).
  • LiveBench (Abacus AI and others): questions refreshed monthly to prevent data contamination, covering reasoning / math / code / language / data / instructions; the strongest ongoing refresh.
  • BFCL (Berkeley Function-Calling Leaderboard): the standard benchmark for tool use / function calling, covering simple / multiple / parallel / multi-turn.
  • GSM8K / MATH / AIME: math-reasoning benchmarks. AIME is the current main battleground for R1 / o1.

In practice: from a 2026 point of view, no single benchmark is trustworthy anymore — you need three layers: cross-checking several benchmarks, your own gold set, and blind human votes on Arena. See E11 and H3.

Eval / Evaluation Evaluation — the “scoring” stage of an LLM app or agent: three layers of evaluation, offline / online / CI

Eval for an LLM or agent application is not a single action; it is a system. Common layers:

  • Offline eval: run the model / prompt / pipeline on a fixed dataset / gold set and read the metrics. Run a regression on every prompt change, automated in CI.
  • Online eval: sample production traffic, and together with A/B tests watch business-metric movement, bad-case detection, and labels from user feedback.
  • Pre-prod eval: before launch, shadow-eval on pre-production traffic (dual-run, don’t return it to the user) and compare trajectory differences between the old and new versions.
  • Adversarial eval / Red team: humans plus automation build adversarial samples (jailbreak, prompt injection, edge cases) and evaluate the safety rails.

How the eval tool stack splits:

  1. General frameworks: OpenAI Evals, DeepEval, Promptfoo, Inspect AI — run evals as a CLI or a library
  2. Built into observability platforms: Langfuse / LangSmith / Phoenix all ship an eval framework tied to traces
  3. RAG-specific: RAGAS (four dimensions, including faithfulness / context relevancy)
  4. Tool-use-specific: BFCL (Berkeley Function-Calling Leaderboard)
  5. Domain-specific: each team’s own gold set plus an LLM-judge rubric

Eval types by how they score:

  • Reference-based (there is a gold answer): exact match, BLEU / ROUGE, unit tests passing, hitting an answer set — objective, but it needs labels
  • Reference-free (no gold answer): an LLM-as-judge gives a 0–1 or 1–5 score; fits open-ended generation and dialogue; judge bias is a major pitfall
  • Pairwise: A vs B comparison, commonly used for model selection; agreement is higher than pointwise
  • User feedback: thumbs up/down, CSAT, retention — the business side’s final acceptance

Rules of thumb: (1) changing a prompt with no eval is changing it blind; (2) the eval model must be ≥ the model being evaluated (the judge principle); (3) the gold set must be versioned and private; (4) every bad case must be regressed into the gold set — the harness-engineering closed loop.

LLM-as-judge Evaluation — use a strong LLM to score candidate outputs in place of human evaluation

Model “evaluation” as an LLM task: the judge model reads (prompt, response) and outputs a 0–1 score / pass/fail / which side wins pairwise. It parallelizes at large scale, is cheap, and can be automated in CI.

Three major biases:

  • Position bias: in pairwise judging, the judge favors A or B
  • Verbosity bias: a preference for longer answers
  • Self-preference: GPT-4 prefers GPT-4 outputs

The judge principle: the judge model’s capability should be ≥ the model being evaluated, or it cannot tell what is good about a stronger model’s answer. The production standard is three layers: your own gold set + an LLM judge + human calibration.

Lost in the Middle Evaluation — in long-context QA, accuracy drops sharply when the key information sits in the middle

The Liu et al. 2023 experiment: put the gold passage at the start or the end of the prompt and accuracy is high; put it in the middle and accuracy falls in a U-shape. With 10+ documents, the middle position can score below a no-context baseline.

Engineering mitigations:

  • Reorder — put the most relevant chunks at the start and the end (a reranker plus head/tail interleaving)
  • Multi-round retrieval plus summarization, instead of stuffing everything in at once
  • Use a model with native long context (Claude / Gemini 1.5 Pro are more stable on RULER)
prompt injection Safety — user input or external content hijacks the model’s behavior and bypasses the system prompt

It is #1 on the OWASP LLM Top 10. Types:

  • Direct injection: “ignore previous instructions, do X”
  • Indirect injection: malicious instructions hidden in a RAG document / web page / PDF / email / tool result — the top threat of the agent era
  • Jailbreak (jailbreak): DAN / role-play / many-shot
  • Payload smuggling: Base64 / Unicode homoglyphs / image OCR injection
  • Tool abuse: make the agent call a sensitive tool

Simon Willison’s conclusion: prompt injection has no 100% solution, and the system must be designed on the assumption that “the LLM is untrusted”. The dual-LLM pattern = a Planner (sees trusted input and decides) + an Executor (sees untrusted input but has no tool permissions).

hallucination / hallucination Evaluation — the model generates content that looks plausible but is actually wrong

Sources:

  • Biased or outdated training data
  • RAG recall that is incomplete or inaccurate
  • Context so long that the signal is diluted
  • The model freewheels (no grounding)

Debug flow: reproduce it and quantify the trigger rate → attribute the cause (RAG recall / whether the model used the context / tool calls) → fix → add a regression → production monitoring (a faithfulness scorer blocks in real time).

Key point: most hallucinations are defects in the prompt / RAG / context engineering, not “the model is sick”.

guardrails Safety — safety rails around each stage of an LLM: input, output, tools, and dialogue

NVIDIA NeMo Guardrails defines 5 kinds:

  1. Input rails: PII redaction, prompt injection detection, topic limits
  2. Dialog rails: control the dialogue flow with the Colang DSL and hard-code critical decision points
  3. Retrieval rails: drop low-quality / sensitive / untrusted chunks
  4. Execution rails: parameter allowlists and authorization checks before a tool call
  5. Output rails: hallucination detection / filtering leaked sensitive data / toxicity filtering

Key point: more rails are not automatically better. Turn on 1–2 high-ROI rails per kind, or latency and cost explode.

jailbreak / jailbreak Safety — bypass the model’s safety training so it outputs harmful content

Common techniques:

  • DAN (Do Anything Now): make the model play an unrestricted AI
  • Role-play: “we’re writing a novel, and character X explains how to do Y”
  • Many-shot (disclosed by Anthropic in 2024): stuff the long context with dozens of fake Q&A examples so the model in-context-learns and answers in kind
  • Crescendo: multi-turn, gradually pulling the conversation onto a sensitive topic
  • Encoding: bypass via Base64 / leetspeak / a low-resource language

Defense: the vendor’s RLHF safety training + application-layer input/output classifiers (Llama Guard) + a cap on max context (against many-shot) + regular red-team exercises.
